## 1. 目的

S Apps の 1 アプリとして、SysML v2 のテキスト表記(`.sysml`)から、規格の図表記に沿った図と表を作る単一 HTML のアプリを作る。用途はハッカソンの講義で、Arduino 複数台からなるシステムを説明・設計すること。生成 AI にテキストを書かせ、アプリに貼って図にする使い方を主とする。

- 1 つのシステムを表す 1 つの `.sysml` から、すべての図と表を作る。
- 入力は SysML v2 の正規のテキスト表記とし、独自の記法を設けない。
- 単一 HTML、サーバーにデータを送らない、ネットなしで動く、の前提は S Apps の他のアプリと同じ。
- ライセンスは MIT。
- リポジトリ名は `sysmlv2`(SysML v1 との取り違えを防ぐため、v2 を名前に入れる)。
- 公開先は `sysmlv2.sapp.jp`。

### 2.2 文法の手当て

基準は仕様書本文の文法とする。本文の文法の誤りは、2.1 Beta 2 の本文に課題番号付きで示された修正によって直す。2.1 Beta 2 にも修正がない箇所だけ、パイロット実装(タグ 2026-03)の文法を根拠に手当てする。課題番号の修正以外に、2.1 の変更は取り込まない(`new` の予約語化などは入れない)。

- 手当ての一覧の正本は `grammar/errata.json` で、57 件とする(E01〜E57)。各件に、規則名・本文の問題・手当て・根拠・本文の行番号を持つ。一覧にない手当てはしない。
- 根拠の内訳: 課題番号 37 件、パイロット実装 18 件、課題番号未特定 2 件(E01 `FilterPackage`、E02 `FunctionOperationExpression`。2.1 Beta 2 に修正はあるが、課題番号を題名から断定できない)。
- E44〜E52 は、公式の例題の受理に必要な本文の誤り 9 件で、2.1 Beta 2 でも直っていないため、パイロット実装を根拠にする。`LibraryPackage`(`standard` を省けない)、`FlowEndSubsetting`(`'.'` がない)、`DefaultReferenceUsage`・`OccurrenceUsagePrefix`(`end` を付けられない)、`SatisfyRequirementUsage`(`assert`・`not` を省けない)、`CaseBodyItem`(本体に `return` を書けない)、`SendNode`(`action a send x;` を読めない)、`EntryTransitionMember`(`then` が二重)、`EnumeratedValue`(前置のメタデータを読めない)。
- 注釈(`AnnotatingElement`)は、パイロット実装に合わせて SysML の `MetadataUsage` を選択肢にする(E42)。
- E53〜E57 は、構文木を正しく作るための本文の誤り 5 件で、2.1 Beta 2 でも直っていない。属性名の誤り 2 件(`OwnedExpressionMember` の `ownedFeatureMember`、`OwnedReferenceSubsetting` の `referenceFeature`)、抽象構文にない型名 2 件(`LiteralReal`、`TypeResultMember` の `ResultParameterMembership`)、参照先の誤り 1 件(`NonFeatureChainPrimaryArgumentMember`)。根拠は抽象構文の該当箇所とパイロット実装。構文木を作るときに読み替えることはせず、すべて手当てとして一覧に載せる。

### 2.3 KerML と SysML の文法の合成

- パーサーは、仕様書本文の SysML と KerML の文法に 2.2 節の手当てを加えたものから作る。
- KerML と SysML に同じ名前の規則があるときは、SysML 側を採る。
- リポジトリの `.kebnf` ファイルは、本文との照合の補助にだけ使う。

### 2.4 字句

- 字句構造は KerML 1.0 の 8.2.2 節に従う。予約語と特殊な終端記号(`DEFINED_BY` など)は、SysML 2.0 の 8.2.2.1.2 節による。規範は 8 章の文法とし、7 章(参考)の説明と食い違うときは 8 章に従う。
- 引用符なしの名前は ASCII の英字・数字・`_` だけ(KerML 1.0 の 8.2.2.3 節)。日本語の名前は `'温度センサ'` のように単一引用符で囲む。
- 単一引用符で囲む名前と文字列に使える「印字可能な文字」は、Unicode の Cc(制御文字、65 文字)・`\`・引用符以外のすべての文字とする。
- エスケープ列は、KerML 1.0 の表 4 の 7 種だけとする。
- 空の名前 `''` は受理する(8 章の文法に従う)。
- 行末は LF・CR LF・CR のどれも 1 つの行末として扱い、混在してもエラーにしない。1 行の注はどの行末でも終わる。
- 空白は、スペース・タブ・フォームフィード・行末だけとする。U+00A0 などほかの空白文字は字句のエラーにする。
- ファイルは UTF-8 として読み、UTF-8 として正しくないバイト列は読み込みのエラーにする。先頭の BOM 1 文字は取り除く。
- 図では、名前を囲む単一引用符を外して表示する(KerML 1.0 の 8.2.2.3 節の注 1)。

### 2.6 解析方式

- 解析は、合成した文法を表として持ち、Earley 法で解釈する方式とする。文法を手で書き写さない。
- 演算子の優先順位と結合性は、KerML 1.0 の 8.2.5.8.1 節の表 6 と注 2 に従って決める。
- 手書きの解析は、検算や速さが要る部分に限って使う。
- 構文木の要素の種類は、要素を作った規則の型から始め、繰り返し(`*`・`+`)の外で代入なしに呼んだ規則の型が今の種類の下位のメタクラスのときだけ、その型に絞る。
- 演算子の優先順位で決まらない曖昧さは、次の規則で解消する。
  - `EndUsagePrefix` の交差の特徴が空の範囲に一致するときは、交差の特徴を作らない。
  - `AssignmentNodeDeclaration` の、対象の束縛と特徴の連鎖の境目では、束縛のある選択肢を採る。
  - 式の本体の中で、名前だけの型付けを要素として読む選択肢は採らない。
- 解析は Web Worker で行い、解析中も入力と画面の操作を止めない。
- 解析が 1 秒を超えたら、進捗バーを表示する。進み具合は、処理した字句の数と、作った木の要素の数から出す。パーサーは、進み具合を知らせる任意の引数を持つ。引数を渡さないときの動きと結果は変わらない。
- テキスト欄の色付けは、見えている範囲(と前後の少し)だけに行い、大きなテキストでも入力を止めない。
- 解析中にテキストが変わったら、実行中の解析を打ち切り、新しいテキストで解析し直す。描画中に「ビュー」か「範囲」を替えたときも、実行中の描画を打ち切り、新しいビュー・範囲で描き直す。処理中は、進み具合の表示だけを出し、範囲の欄・図・診断に「候補がない」などの結果を出さない。
- 構文上正しいテキストは、入れ子の深さや式の長さによらず読む。解析・名前解決・描画の処理は、入れ子の深さや式の長さに比例して呼び出しを深くしない(呼び出しの深さの上限で止まらない)。

### 3.2 グリッドビュー(表)

- 表は、SysML 2.0 の 9.2.20.2.5 節の GridView(要素と関係を格子に並べて示すビュー。下位に表・値の表・関係のマトリクスがある)にあたるものとして、「ビュー」の選択欄の「グリッドビュー」(値 `grid`)で画面に出す。選ぶと、下の 4 つの表を縦に並べて出す。図表記の規格はないので、表の中身と形はこのアプリで決める(部品の一覧・ポートと接続先・要求と満たす部品は下位の「表」、機能の割り当て表は「関係のマトリクス」にあたる)。
- 作る表は次の 4 つとし、この順に縦に並べる。行は記述の順とする。描く範囲は 5 章のとおりとし、パッケージのときは入れ子のパッケージの中も含める。
  - 部品の一覧: 部品の使用(入れ子の部品を含む)を 1 行にする。列は「部品」(名前)・「型」・「持ち主」(持ち主の修飾名)・「多重度」・「説明」(`doc` の本文)。
  - ポートと接続先: 部品の使用ごとに、そのポート(型の定義から受け継いだものを含む。相互接続ビューで描くものと同じ)を 1 行にする。列は「部品」・「ポート」・「向き」・「型」・「接続先」(相手の部品.ポート)・「つなぎ方」(`connect`・`interface`・`flow`・`bind` など。インターフェースは型の名前も書く)。Arduino のピンの割り当て表として使う。
  - 要求と満たす部品: 要求の定義と使用を 1 行にする。列は「要求」・「種類」(定義・使用)・「型」・「本文」(`doc`)・「満たす部品」(`satisfy … by …`)・「検証」(`verify` する検証)。
  - 機能の割り当て表: 行を、`perform` か `allocate` で部品に割り当てた行動、列を、その部品とするマトリクス。セルには `perform`・`allocate`(両方なら `perform, allocate`)を書く。
  - 1 つのセルに値が 2 つ以上あるときは「、」で区切る。行が 0 の表は、題と「該当なし」の 1 行だけを出し、ボタンは置かない。
- 表の出し方と保存は、S Apps のプロジェクト計画・プロジェクト分析に合わせる(9.1 節・9.3 節)。表を SVG・PNG・PDF とタブ区切りの文字で出し、Markdown・TeX・HTML の書き出しは作らない。TeX の報告書には PDF を貼る。

## 4. 配布形態

- 5 つのビューと表を、1 つの HTML にまとめることを基本方針とする。1 つのモデル(1 つのテキスト、またはフォルダの中の複数のテキスト。9.4 節)から、すべてのビューを画面で切り替えて見られることを優先する。
- 画面の確かめ: Worker との受け渡しを含む画面の動きは、ブラウザで開いて確かめる。開発の環境にブラウザがないときは、ブラウザの `MessageEvent` と同じ形(`{ data: … }`)の受け渡しで画面のスクリプトを動かす検査を置き、ビルドした HTML のブラウザでの確かめはオーナーの側で行う。
- 速さの目安(作業の機械の Node.js での実測): 部品 300 個を鎖のようにつないだ部品の相互接続ビューを 5 秒以内に描く。`view` の `expose X::**` で描く図は、入れ子のパッケージの中まで描くので、範囲で描く図とは描く量が違う。時間は記録するだけにする。
- ビューごとの HTML に分けるのは、大きさや速さで実用上の問題が実測で出たときだけの退路とする。ビューを足すたびに、HTML の大きさ、開くまでの時間、解析の時間、使用メモリを測って記録する。
- どのビューでも文法全体で解析するので、分けてもパーサーは小さくならない。分けて小さくなるのは、各ビューの描画部品と記号の定義である。
- 分けることになっても作り直しにならないよう、各ビューの描画と表の書き出しを独立した部品にする。ビルドの設定 1 つで、1 つにまとめた HTML とビューごとの HTML の両方を、同じソースから出せるようにする。
- ビルドは、外部のパッケージを使わず、Node.js で動く自作のスクリプトで行う。Node.js を使うのはビルドと検査だけで、出来上がった HTML には含まれない。HTML はブラウザだけで動く。
- ビルドは、まとめた HTML の中で、各ファイルが読み込む(`import` する)名前が、読み込む先のファイルの書き出し(`export`)にすべてあることを確かめ、1 つでもなければ失敗する(検査はソースのファイルを Node.js で直接読むので、まとめ方の誤りを見つけられないため)。
- 解析を行う Web Worker は、HTML の中に入れたコードから作る。
- 画面で選べるビューは、ビルドの設定(`tools/build/config.json` の出力ごとの `views`)で決める。1 つにまとめた HTML(公開するアプリ本体。`dist/index.html`。11 章の「公開の形」)には、作ったビューをすべて入れる。ビューごとの HTML は、同じソースから出せることを確かめるため、相互接続ビューだけのもの(`out/build/sysmlv2-interconnection.html`。公開しない)を出し続ける。
- 実測の記録(図からの編集の段階 2・3 の後): 1 つにまとめた HTML は 965,342 バイト。作業の機械の Node.js で、一般ビューの 1 候補を描く時間は、最初の描画を除いて最大約 2.2 秒、プロセスの最初の描画は約 2.7〜3.0 秒(標準ライブラリの大きいパッケージ)。生徒の規模の入力(部品の定義と使用が約 30 個)は、ヘッドレスの Chromium で 0.1 秒未満。Windows の Chrome・Edge でも、図の見た目と中身の直しの後まで確認の手順どおりに動いた。1 つの HTML のままで問題はない。
- ビューごとの HTML は、今は選べるビューを絞るだけで、描画の部品は入れたままにしている(相互接続ビューだけの HTML も 965,281 バイト)。分けて小さくする必要が実測で出たときに、ビルドで部品を外す仕組みを作る。

## 5. 入力の扱い

- 構文は、2 章の文法全体で解析する。構文上正しいテキストは必ず読み、構文上誤ったテキストは必ずエラーにする。どのビューを表示していても同じ。
- 図には、そのビューで描く要素だけを出す。描かない要素があることは誤りとしない。
- 描く範囲は、テキスト中の `view` と `expose`(8.2.2.26 節)に従う。`view` が書かれていなければ、アプリが候補(部品を入れ子に持つ部品など)を一覧にし、画面で選ばせる。画面で選んでも、テキストは書き換えない。
- 画面で選んでいる範囲を `view` 宣言としてテキストに書き足すコマンドを用意する。利用者が実行したときだけ書き足す。
  - 書き足す形: `view 名前 : StandardViewDefinitions::ビューの定義 { expose 範囲::**; }`。ビューの定義は今のビューのもの(`GeneralView`・`InterconnectionView`・`ActionFlowView`・`StateTransitionView`・`SequenceView`・`GridView`)。範囲は、書き足す場所から範囲の要素に解決する名前(必要なら修飾名)で書く。
  - 書き足す場所: 範囲の要素の持ち主のパッケージの、最後のメンバーの後ろ(閉じ括弧の前)。範囲がパッケージなら、その持ち主のパッケージとする(範囲の中に置くと、`expose 範囲::**` が `view` 自身を公開するため)。持ち主のパッケージがなく根の名前空間なら、ファイルの末尾とする。字下げは、書き足す場所の前のメンバーに合わせる。
  - 名前: 「範囲の名前の」+ビューの日本語名(例: `'要求の一般ビュー'`)。書き足す場所の名前空間に同じ名前があれば、末尾に 2、3、… を付ける。引用符は 8 章の名前の変更と同じ規則で付ける。
  - 根の名前空間など、名前で指せない範囲では、コマンドを実行せず、理由を表示する。
  - 書き足した後のテキストを解析し直し、構文エラーがなく、書き足した `view` の範囲の名前が範囲の要素に解決し、モデルの差分が足した `view` とその中身だけであることを確かめる。満たさなければ書き足す前に戻す。書き足しは取り消せるようにする(8 章と同じ)。
  - テキストに `view` が 1 つでもあると、描く範囲の候補は `view` だけになる(下の規則)。コマンドを実行すると、ほかの候補は選べなくなる。
- `view` で描くのは、`view` が所有する `expose` で公開した要素のうち、`filter` の条件を満たすものだけとする(SysML 2.0 の 8.3.26.11 節)。箱の中にも、公開した子だけを描く。`expose X;` なら X の箱だけを描き、中は空にして左下に `...` を出し、診断に「中を描くには `expose X::**;` と書く」と案内する。`expose X::*`・`X::**` は、X の見える Membership(import で取り込んだもの、型なら受け継いだものを含む)を公開する。`expose X::**` は X 自身も公開し(KerML 1.0 の 8.3.2.4.4 節 MembershipImport の `importedMemberships`「Returns at least the importedMembership」)、`expose X::*` は X 自身を公開しない(8.3.2.4.6 節 NamespaceImport)。
- `filter` の条件は、`view` が所有するものと、型にした `view` の定義(利用者のモデル)から受け継いだものを当てる。`expose X::**[…]` の角括弧の条件も同じ扱いとする。
- `filter` と角括弧の条件は、`@種類名`(`@SysML::PartUsage` など)と `@利用者の注釈` の形だけ反映する。それより複雑な式の条件(`not` を含むものなど)は反映せず、反映していないことを表示する。`@種類名` は、要素の種類がそのメタクラスに適合すれば通す(7.8 節)。`@利用者の注釈` は、要素が所有する注釈のメタデータが、そのメタデータ定義(下位の定義を含む)で型付けされていれば通す。
- `filter` で親の箱が除かれて子だけが残ったときは、図にある最も近い祖先の箱の中に描く。祖先の箱がなければ最上位に描く。
- `view` の中の `render` は反映せず、反映していないことを表示する。
- どのビューで描くかは、画面の切り替えを優先する。`view` の型は、開いたときの最初の表示に使う(最初の `view` の型が `StandardViewDefinitions` の標準のビューの定義か、それを特殊化した利用者のビューの定義なら、そのビューにする)。その HTML でそのビューを選べないときは、相互接続ビューで表示し、その旨を図の診断に出す。`view` がない、最初の `view` の型が標準のビューでない、「新規」のときは、一般ビュー(SysML 2.0 の 9.2.20.1 節の表 34 で、パッケージの既定の区画)で開く。その HTML で一般ビューを選べなければ、今のビューのままとする。`view` が複数あれば、描く範囲の候補の一覧に並べる。
- 描く範囲の候補は、テキストに `view` があれば `view` を記述の順に並べる。なければ、ビューごとに次のものを、入れ子のものも含めて記述の順に並べる。
  - 相互接続ビュー: 部品・ポート・接続を所有する部品の定義と使用。
  - 状態遷移ビュー: 状態・遷移を直接所有する状態の定義と使用(`exhibit state` を含む)。
  - 一般ビュー: パッケージ(根の名前空間を含む)。パッケージが直接持つ定義と使用と、その間の関係を描く。
  - グリッドビュー: パッケージ(根の名前空間を含む)。型が `GridView`(またはそれを特殊化した定義)の `view` があれば、その `view`。
  - シーケンスビュー: メッセージか、頭を経る事象の間の継承を直接所有する、部品の定義と使用、オカレンスの定義と使用(種類がちょうど `OccurrenceDefinition`・`OccurrenceUsage` のもの)。頭のないものは候補にしない。
  - アクションフロービュー: 行動・継承・フローを直接所有する行動の定義と使用(`perform` の行動を含む)と、計算・解析・検証・ユースケースの定義と使用(7.5 節)。状態・遷移・フロー(どれも行動の下位の種類)、一般の `case`、if・ループの本体(名前のない行動)は候補にしない。

## 6. 名前解決と内蔵する名前

### 6.1 標準ライブラリと内蔵する表

- 標準ライブラリ(のファイル)は同梱しない。
- 標準ライブラリの名前の索引を内蔵する(`grammar/library_index.json`。`src/model/` に、そこから道具で生成した表を置く)。索引は、仕様の一部である標準ライブラリのファイル(SysML 2.0 の 2 章・9.1 節。10 章の照合用にタグ 2026-03 から取得するもの)から、道具 `tools/model/extract_library.mjs` で抜き出して作る。手で書き写さない。
  - 索引に入れるのは、名前解決に要るものだけとする: 要素ごとの修飾名、名前、短い名前、種類(メタクラス)、持ち主、可視性、上位の型(特殊化・部分集合・再定義・型付け・共役)、別名の相手、import(対象と、再帰・可視性)。
  - 入れないもの: `doc` と注の本文、式・値・本体、図や表示に関わるもの。ファイルそのものも、リポジトリに入れない(11 章)。
- アプリは、描画と名前解決に必要な名前と、要素の種類(メタクラス)の表を内蔵する。正本は `grammar/builtin.json` で、各項目に本文の節と行番号を持つ。`src/model/builtin_table.js` は、正本から道具で生成する。
- 内蔵するもの:
  - 要素の種類 182 件(KerML 84、SysML 98)と、それぞれの直接の上位の種類。出典は KerML 1.0 と SysML 2.0 の 8.3 節。
  - 6 つの標準ビューの定義(一般・相互接続・アクションフロー・状態遷移・シーケンスと、表に使うグリッド)の名前・短い名前(`gv`・`iv`・`afv`・`stv`・`sv`・`grv`)・上位の定義。出典は SysML 2.0 の 9.2.20.2 節(グリッドは 9.2.20.2.5 節)。
  - アクションの `start`・`done`(SysML 2.0 の 9.2.10.2.4 節)。`ActionDefinition`・`ActionUsage` に適合する要素は、これを受け継ぐ。
  - パッケージ `KerML`(下位のパッケージ `Root`・`Core`・`Kernel` を持つ)、`SysML`、`StandardViewDefinitions`、`Actions`。`SysML` は、本文(SysML 2.0 の 9.2.22 節)どおり、メタクラスを下位のパッケージなしで直接持つ。標準ライブラリのファイルにある `SysML::Systems::PartUsage` の形の名前は、未検査になる。
- 内蔵する名前と表(上の索引を除く)は、仕様書本文(抽象構文と標準ライブラリの章)を出典として作る。
- 標準ライブラリの要素への参照は、索引の要素に解決する(診断では解決済み)。索引の要素は、図には箱として描かず、型などの文字にだけ名前を出す。図からの編集の対象にもしない。索引にない名前への参照は、エラーにせず「未検査」とする。
- 索引は、`src/model/` の定数 1 か所で切れる。切れば、索引を入れる前の扱い(上の表の項目以外の標準ライブラリへの参照は未検査)に戻る。
- 利用者のモデル内で定義された名前(利用者が定義した単位や注釈を含む)は解決する。

### 6.2 名前解決の規則

- 基準は KerML 1.0 の 8.2.3.5 節とする。参照を探し始める名前空間(局所の名前空間)は、参照を持つ関係の種類によって、8.2.3.5.2 節の表で決める。
- 式の中の名前の参照(`FeatureReference`・`InstantiatedTypeReference`)も、参照として扱う。
- 各参照は、次を持つ。
  - 解決済み・未検査・曖昧のどれか。解決済みの解決先は、利用者のモデルの要素か内蔵する表の項目。
  - 原文の範囲。修飾名の区切りごとの範囲と解決先も持つ。
  - 解決した要素の種類が、文脈で期待される種類に適合しないこと(KerML 1.0 の 8.2.3.5.1 節)。
- 逆引き(ある要素を指す参照の一覧)を作れるようにする。修飾名や特徴の連鎖の途中の区切りとして、その要素を通る参照も含める。

本文に定めがない点と、本文の読み方を決めた点は、次のとおりとする。

| 点 | 扱い |
|---|---|
| 根の名前空間での単純な名前 | 根の名前空間の所有と import を先に探し、なければ大域の名前空間を探す |
| 曖昧 | 1 つの名前空間の局所の解決で、別々の要素が 2 つ以上当たれば曖昧とする(再定義で除かれるものは除く)。大域で 2 つ以上の根の名前空間に当たる場合も曖昧とする。曖昧は意味エラー S2(9.2 節)とは別のもので、図からの編集を止める印として使う |
| D3 の印 | 索引を入れたときは、暗黙の特殊化の相手と、上位の型が索引の要素である名前空間は、索引のメンバー(受け継ぐものを含む)で本文どおりに局所の解決を行い、D3 の印の理由にしない(ライブラリのメンバーに遮られる名前は、そのメンバーに解決する)。索引にない上位の型・対象のわからない import・評価できないフィルター条件(解いている名前自身を含むフィルター条件を含む)は、下の規則のまま印の理由にする。索引を切ったときは、次の規則による。次のどれかを持つ名前空間を通り越して、外側で見つかった参照には、D3 の印を付ける: 暗黙の特殊化(すべての型は標準ライブラリの型を特殊化する)、対象のわからない import、評価できないフィルター条件。ライブラリの名前に遮られているかもしれないからである。ただし暗黙の特殊化は、参照の名前(書かれた区切りの名前)が空白か ASCII 以外の文字を含むときは印の理由にしない。標準ライブラリの型(Domain Libraries の Quantities and Units のパッケージのものを除く)のメンバーの名前(受け継ぐものを含む)は、どれも空白を含まず ASCII の文字だけからなり、そのような名前と同じになりえないからである。明示の特殊化・型付けなどで、上位の型が未検査(利用者のモデルにも内蔵する表にもない)の名前空間は、この理由づけが当たらないので、今のとおり印を付ける。このことは、10 章の照合用の標準ライブラリのファイルで検査して確かめる(名前はアプリに写さない)。診断では解決済みとして表示し(9.2 節)、図からの編集の前の検査では未検査と同じに扱う(8 章) |
| 特徴の連鎖の 2 番目以降の区切り | 前の区切りの特徴に対する見える解決とする(`public` だけ。継承した `public` を含む。外側へ進まない) |
| 再定義の名前(`:>> x`) | 所有する型の上位の型ごとに、局所の解決(継承を含む)で探す。なければ、その上位の型の外側へ完全な解決で進む。上位の型が利用者のモデルになく暗黙の特殊化だけなら、未検査とする。所有する型が `ActionDefinition`・`ActionUsage` に適合するときは、内蔵する `Actions::Action` も上位の型として探す |
| 遷移の始点・終点 | `TransitionUsage` 自身から探し始める |
| 共役ポートの名前 `~A` | `A` を `PortDefinition` に解決し、その共役ポート定義(原文にない暗黙の要素)を解決先とする。逆引きでは `A` への参照として数える |
| フィルター付きの import と、パッケージの `filter` | 条件が `@種類名`・`@利用者のメタデータ定義` の形だけなら評価する。それ以外の条件を通る名前は未検査 |
| 式の結果から先の名前(`a.b` の `a` が式) | `a` が名前の参照か特徴の連鎖なら、その特徴から探す。それ以外の式の結果から先の名前は未検査 |
| `assign` の対象の連鎖 | 最初の引数の値の式が指す特徴に対する見える解決とする。値の式が名前の参照か特徴の連鎖でなければ未検査 |
| 特徴の値の式の中の名前 | 本文どおり、値を持つ特徴そのものから探す |
| 8.2.3.5.2 節の表にない関係(注釈の `about`、依存、型の特徴づけ、素であること、合併・交差・差、特徴の逆) | 関係を所有する名前空間から、完全な解決で探す |
| `$::A` | このファイルの根の名前空間の見える要素を先に探し、なければ大域の名前空間(フォルダのほかのファイルの根の名前空間、索引、内蔵する表)を探す |
| 複数のファイル(9.4 節) | ファイルごとに根の名前空間を作る。大域の名前空間は、読み込んだすべてのファイルの根の名前空間と、標準ライブラリ(索引)と内蔵する表からなる。2 つ以上の根の名前空間に当たる名前は、上の「曖昧」の規則どおり曖昧とする。解決の結果は、ファイルを読み込む順によらない |
| 暗黙の再定義 | 利用者のモデルの特徴どうしの端・引数・結果の暗黙の再定義(KerML 1.0 の 8.4.2 節の `checkFeatureEndRedefinition`・`checkFeatureParameterRedefinition`・`checkFeatureResultRedefinition`)を入れる。継承で再定義された特徴を除くとき、名前を宣言していない特徴の実効の名前を求めるとき、上位の型をたどるときに使う。標準ライブラリの特徴を再定義する制約は入れない。引数の位置は、上位の型の引数を受け継いだものも含めて数える(`checkFeatureParameterRedefinition` の説明の文に従う。式は上位の型の所有する特徴だけで書いてあるが、説明と式が食い違うときは説明の意図に従う)。向きを書かない `subject`・`actor` なども引数とみなし、上位の型が `perform a.b` の連鎖なら、連鎖の先の引数を見る |
| 呼び出しの型 | 呼び出しの式(`InvocationExpression`)と、`new` の結果(`ConstructorExpression` の結果)は、呼び出しの型を上位の型に持つ(KerML 1.0 の `checkInvocationExpressionSpecialization`・`checkConstructorExpressionResultSpecialization`) |
| 遷移の受け取りの引数 | 引き金の受け取りのアクションの最初の引数から、名前(SysML 2.0 の 8.3.6.3 節の naming feature)と上位の型(8.3.18.9 節の `checkTransitionUsagePayloadSpecialization`)を受け継ぐ |
| 解決中の import とフィルター条件 | 解決中の import と、解決中の名前を含むフィルター条件は除いて先へ進む。除いたのが、いま解いている参照そのものの import なら、結果を確定させる。それ以外なら結果を仮とし、全体を解いた後に、どの参照の状態と解決先も変わらなくなるまで解き直す(上限 20 回) |

## 7. 図表記

### 7.1 記号

- 記号は、仕様書の図形を読み取って描き起こす。仕様の記号 SVG ファイルはアプリに入れない。
- 記号ごとに、図表記文法の生成規則名と描き起こした図形の対応を一覧で管理する(`tools/view/symbols.json`。生成規則名・本文の節と行番号・PDF の図のページ・抽象構文の要素の種類)。描き起こしは、作るビューで使う記号から順に行う。
- 規範とするのは記号の形・区画・接続関係とする。記号の配置は自由で、内容に合わせて伸ばしてよい。線は直線でも曲線でもよく、交差箇所の跳び越し記号も使える(8.2.3.1 節)。
- 相互接続ビューで描くのは、図表記文法の `interconnection-view` から展開される生成規則のすべて(`interconnection-element` の全選択肢と、注釈・依存)とする。ほかのビュー(一般・アクションフロー・状態遷移・シーケンス)の図を中に持つ区画は、相互接続ビューの中には描かず、描いていないことを表示する。文字だけの区画(`exhibit states` など)は描く。ほかのビューの図は、そのビューに切り替えて見る。
- 状態遷移ビューで描くのは、図表記文法の `state-transition-view` から展開される生成規則のすべてとする(7.4 節)。アクションフロービューで描くのは、`action-flow-view` から展開される生成規則のすべてとする(7.5 節)。`state-subaction-body` の図の形、行動の `then body`・`else body`・`loop body` は、7.5 節の規則で、どちらのビューでも図として描く。
- 本文の図表記文法の書き誤りは、次のように読む。`cdot-def-label`・`element-in-textual-compartment`・`states-actions-compartment`・`include-actions-compartment` は、それぞれ定義のある `cdef-label`・`element-inside-textual-compartment`・`state-actions-compartment`・`include-use-cases-compartment` と読む。`usage-node =`(8.2.3.20・8.2.3.21 節)は `=|` と読む。`concerns-compartment`・`performed-by-compartment` は区画の選択肢に入れる。見出し `'satify requirements'` は `satisfy requirements` と表示する。`ends-compartment-element` の `QualifedName` は `QualifiedName` と読む。`action-name-compartment` などの `usage-name-with-alias<` の `<` は描かない。`exhibit-state-scompartment-element` は `exhibit-states-compartment-element-compartment`、`usage-edge = |transition …`(8.2.3.18 節)は `=|` と読む。
- 本文に定義のない生成規則は、次のように読む。`port`(8.2.3.12 節の `interconnection-element`)は辺の記号 `port-l`・`port-r`・`port-t`・`port-b`、`port-node` はポート、`stakeholder-node` は `stakeholder`、`message-connection` は `message`、`proxy` は `proxy-v`・`proxy-h` と読む。`flow-label` の 2 つの定義は、線には 13925 行の形、線の上の印には 14000 行の形を使う。`state-node`・`state-ref-node` は `state`・`state-ref` と読む。`assign-action-expression` は、`assign` の後ろの原文(`AssignmentNodeDeclaration` の対象 `:=` 値)とする。
- これ以外の本文の不整合は、読み替える前に問として挙げ、裁定を受ける。

### 7.2 相互接続ビューの描き方

- 図の枠(`framed-view`)は、テキストの `view` で描く範囲を決めたときだけ描く。左上に `«view» 名前 : 型`、右上に `expose`、左下に `view` が所有する `filter`、右下に `view` の注を書く。画面で候補を選んだときは枠を描かない。
- 描く範囲が部品の定義なら、外側の箱は `part-def`(角の尖った四角)とする。部品の使用なら `part` とする。範囲の中の入れ子の部品の定義は、文字の区画(`features`)に出す。
- ポートは、持ち主の箱の辺に描く。ポートの箱(`port-usage`)は、持ち主の箱が図にないポートにだけ使う。入れ子のポートは、所有するものだけを描く。
- ポートの向きの矢印は、ポートの使用に書いた向きだけで決める。`in` は箱の内向き、`out` は外向き、`inout` は両向きとする。向きのないポートは矢印を描かない(7.8 節)。共役ポートでも、使用に書いた向きを反転しない。
- 型の定義のポートは、受け継いだポートとして、ラベルの先頭に `^` を付けて箱の辺に描く。受け継ぐ範囲は、名前解決(6.2 節)と同じ上位の型のたどり(特殊化・型付け・部分集合・再定義・共役)とする。使用の中で再定義したポートは、受け継いだものの代わりになる。`view` がなく画面で候補を選んだときは、受け継いだポートをつながりの有無によらず全部描く。`view` で描くときは、公開されたものだけを描く。
- 接続の端が解決できない・未検査のとき、またはポートでない特徴のときは、辺の上の黒丸(`proxy-v`・`proxy-h`)と特徴の連鎖のラベルで描く。
- 接続とインターフェースの使用は、いつも線で描く。端が 2 つなら `connection-graphical`・`interface-connection`、3 つ以上なら `n-ary-connection` とする。矢じりのある接続の形と、接続を箱で描く形(`connection`・`interface`)、線と箱を結ぶ点線(`connection-*-elaboration`)は使わない。接続の定義は箱(`connection-def`)で描き、`ends` の区画には `端の名前 : 型` の形で書く。
- 接続の線の端の名前(rolename)は線の上、多重度は線の下に、どちらもその端の近くに置く。接続の名前は線の上の中ほどに置く。
- 接続の端が描く範囲の外の要素に解決したときは、その接続を描かず、診断に「描いていない接続」として出す。
- フローは、端の特徴の連鎖をたどり、図に描いたポート(なければ箱)の間に、塗りつぶした三角の矢じりの線を引く。連鎖が描いたものより先に続くときは、端のラベルに残りを書く。接続・インターフェースが所有するフローは、その線の上の印(`flow-node-r` など)で描く。
- メッセージ・フロー・継承フローのラベルは、線の上の、線の近くに置く。置けないときだけ線の下の近くに置く。
- 制約と要求の引数(`ParameterMembership` が所有する向きのある特徴)は、箱の辺に `param-*` で描く。`subject` などは `distinguished-parameter` で描く。`actor` は棒人間の形で描く。
- 図形で描かない所有メンバーは、種類に合う文字の区画に、宣言の原文(本体の `{ … }` を除き、空白をつめたもの)で出す。合う区画がなければ `features` に出す。パッケージの区画(`packages`・`members`・`relationships`・`doc`)は使わない。`variant` の要素は箱にせず、`variants` の区画に出す。中に図を持たない箱(項目・ポートの定義・制約など)が所有する線と部品も、文字の区画に出す。
- 接頭辞のメタデータ(`#Safety part x`)は、名前の区画のキーワードの行(`«#Safety part»`)に書く。
- 原文に書かれていない暗黙の要素(原文の範囲が空のもの)は描かない。
- 箱の中に描いていないメンバー(ほかのビューにしか現れない要素、`filter` で除いた要素、`expose` で公開していない要素)があるときは、その箱の左下に `...` を出し、何を描いていないかを診断に出す。
- 線の太さは、すべて同じにする。

### 7.3 配置と線

- 初版は自動配置だけとする。利用者が箱を手で動かす機能は持たない。
- 自動配置は、記述の順に並べる方式とする。入れ子の箱を記述の順に格子状に並べ(1 行に ceil(√n) 個)、箱の大きさは中身に合わせて決める。線は直角に曲げて引く。関係のない箇所を直したときに、並びがほとんど変わらないことを優先する。
- ポートを置く辺は向きで決める。`in` は左、`out` は右に置く。`inout` と向きのないポートは、最初につながる相手のある側に置き、つながりがなければ上に置く。上と下の辺では、ポートの間隔をラベルの幅に合わせて広げる。
- 線は、ほかの箱・注の記号・ポートの記号を避けて引き、避けられないときだけ横切る。箱の縁に沿って走らせず、ほかの線と重ねたり並べたりせず、短い区間で折れて戻る回り道(コの字)を作らない。同じ辺に着く線は着く点を分ける。
- 注の記号の置き場所: 線が注から出る注釈の線 1 本だけの注で、注釈先(ポート・引数・`proxy` なら持ち主の箱、区画の行ならその箱、入れ子の要素ならその祖先)が注と同じ領域の要素のときは、注を注釈先の近くに置く。注釈先のマスの右か下(一般ビューは下を先に、ほかのビューは右を先に見る)の空いたマスに置き、なければ注釈先の右に新しい列を足す(注釈先が右の端の列なら、下に新しい行を足す)。図の右の端の列より右のマスは空きに数えない。列(swimlane)と 1 行の並びの領域では動かさない。注を動かした図の (a)〜(e) が、動かさない図より 1 つでも増えるときは、その図では注を動かさない(図ごとの確かめ。動かした図の (a)〜(e) がすべて 0 なら描き比べない)。
- 持ち主の箱への注の線は、注の記号から持ち主の内側の縁の近い点へ、ほかの記号を横切らずに引く。区画の中の要素に付く注の線は、その要素の文字(灰色にした部分)まで引く。区画の行に着く線(注・依存・割り当てなど)は、行の左か右の、相手に近い側から着け、行の文字に重ねない。
- 行為者(棒人間)は名前を下に書くので、行為者に着く線は下の辺に着けない。線は棒人間の図形(頭と体)に着け、上から来る線は図形の上の中央(頭の上)、左右から来る線は腕の高さで手の先に着ける(名前を含めた外接矩形の縁には着けない)。
- 文字(ラベル・端の名前・多重度)は、ほかの文字・線・箱の縁に重ねない。足りなければ、箱の間隔や線の長さを広げる。
- 文字の幅は、ブラウザで測らず、文字の種類ごとの幅の表から決める(10 章の決定性のため)。表示の字体の違いに備えて、余裕を持たせる。
- 線と生存線には、見た目を変えない、幅 10 px の見えない当たり判定を重ね、クリックしやすくする。当たり判定は、すべての見える線より下の 1 つの層にまとめ、各当たり判定に、その線(生存線ならその頭)と同じ要素の印と原文の範囲を付ける。図の質の検査では数えず、保存する画像にも写さない。
- 線を引く順番は、線の要素の記述の順とする。関係のない行を書き足しても、すでにある線どうしの順番が変わらないようにする(線の番号の文字列の順にはしない)。
- 注の置き場所、行為者の節点、パッケージの箱、外側の箱の大きさ、計算とケースの候補の規則(7.3・7.5・7.6・7.7 節)は、`src/view/index.js` の定数 `FIG14` の項目(`N`・`A`・`P`・`F`・`C`)で切れる。
- 線を引き終えた後、すべてのビューで、線の端の仕上げを行う。矢じりがほかの線の矢じりと重なる線、ほかの線が辺を横切る位置の近くから出る線、終点の手前に小さな段がある線を、ほかの条件を悪くしない範囲で引き直す。

### 7.4 状態遷移ビュー

- 状態遷移ビューで描くのは、図表記文法の `state-transition-view` から展開される生成規則のすべて(状態の定義と使用、`exhibit state`、遷移、継承、`state-transition-node` の全選択肢と、注釈・依存)とする。開始・終了・分岐・合流などの節点、行動の箱、`else-branch` は、アクションフロービュー(8.2.3.17 節)と共通の部品として作る。`exhibit-edge` は描かない。
- 外側の箱は、状態の定義なら `state-def`、状態の使用なら `state`(参照なら `state-ref`)とする。描く範囲が `exhibit state` のときは `state` の形にし、名前の区画だけを `exhibit-state-name-compartment`(1 行目 `«exhibit-state»`、2 行目 `«state»`)にする。`state-transition-compartment` は使わず、状態の箱が入れ子の状態を直接持つ。
- 状態の箱は、名前の区画(`parallel` なら `«parallel»` の行)、entry・do の区画、入れ子の状態、exit の区画、文字の区画の順に並べる。
- `entry`・`do`・`exit` は、原則として状態の箱の区画に、宣言と本体 `{ … }` を文字で書く(見出しは斜体にしない)。本体に行動・継承・フローがあるときは、本体を区画の中にアクションフローの図(7.5 節)として描く。遷移・継承の端になるものと、持ち主の状態の箱が図にないものは、節点で描く。宣言も本体もない空の `entry` は、黒い角の丸い四角(`entry-action` のもう 1 つの形)、それ以外は `entry-action`・`do-action`・`exit-action` の箱とする。
- `start-node`(黒丸)と `done-node`(二重丸)は、内蔵の `start`・`done` を参照する端だけに使う。
- 状態の中の行動と、`view` で公開した行動は、`action`(参照なら `action-ref`)の箱で描く。名前の区画は行動の種類ごとに 8.2.3.17 節の区画(`«accept action»`・`«send action»`・`«assign»`・`«if»`・`«loop»`・`«perform action»`)とし、その下に式を書く。accept・send・assign は `accept`・`send`・`assign` の後ろの原文を区切り線なしで書き、if・while・for は見出しのある区画(`if condition`・`while condition`・`until condition`・`for iterator`)に書く。`then body`・`else body`・`loop body` は、本体を区画の中にアクションフローの図(7.5 節)として描く。
- 遷移は実線と開いた矢じりで描く。ラベルは、引き金(`accept` の宣言)・ガード `[式]` の行と、`/ 効果` の行に分け、あるものだけを書く。`/` は効果があるときだけ書く。遷移の名前は書かない。分岐から出る遷移のラベルはガードだけとし、`else` は `else-branch`(破線・`else`)で描く。継承(`st-succession`)は、いつも実線で文字なしとする。
- 始点や終点を省いた書き方の端は、7.8 節の規則で求める。求まらない、または端が図にない遷移・継承は描かず、図の診断に「描いていない遷移」として出す。
- 状態の箱の中の入れ子の状態は、同じ状態遷移ビューとして箱の中に描く。中に描いていないメンバーがある箱には、左下に `...` を出す。注釈・依存・文字の区画・図の枠は、相互接続ビューと同じ部品で描く。
- 配置と線の規則は、7.3 節と同じとする(記述の順の格子。開始の節点は先頭に置く)。加えて、次のようにする。
  - 遷移のラベルが置けるよう、線を持つ箱では、格子の間隔と左右の余白をラベルの幅に合わせて広げる。
  - 自分自身に戻る遷移は、箱の角を回る形で引く。
  - 小さい節点(円・ひし形・棒)に着く線どうしは、矢じりが重ならないよう、着く点や辺を分ける(線の端の仕上げは 7.3 節)。
- 図の質の検査(10 章)も同じものを当てる。

### 7.5 アクションフロービュー

- アクションフロービューで描くのは、図表記文法の `action-flow-view` から展開される生成規則のすべて(行動の定義と使用、`perform` の行動、参照の行動、`action-flow-node` の全選択肢、`action-flow-relationship` の全選択肢、部品ごとの列 `perform-actions-swimlanes`、注釈・依存)とする。継承フローとメッセージも、相互接続ビューと同じ記号で描く(7.8 節)。
- 節点、行動の箱(種類ごとの名前の区画と式の区画)、`else-branch` は、状態遷移ビューと共通の部品を使う(7.4 節)。送信・受信の行動の箱の左上の印は、アクションフロービューだけに描く。行動の引数は箱の辺に `param-*` で描き、`proxy` の形はアクションフロービューの中だけで使う(SysML 2.0 の 8.2.3.17 節の注)。行動の定義の箱の下の辺は、相互接続ビューの `part-def` と同じく太くしない。
- 計算(`calc`)と、解析・検証・ユースケースの定義と使用も、行動・継承・フローを直接持つときは、アクションフロービューで描く(SysML 2.0 の 8.2.3.19・8.2.3.23〜8.2.3.25 節で `action-flow-element` に足されている)。外側の箱は、その種類の名前の区画(`«calc def»`・`«analysis def»` など。一般ビューの分野ごとの記号と同じ文字)と辺の引数で描き、中の図はアクションフローの図の規則で描く。一般の `case` と `include use case` は、図表記に記号がないので候補にしない。中の計算・ケースの使用は行動として描かず、文字の区画に出す。
- 外側の箱(アクションフロービューの最上位の箱と、状態遷移ビューの中の本体の図の箱)の大きさは、中身(領域の要素と、辺のポートのはみ出し・ラベル)の外接矩形に、左と上の余白と同じ値を足したものとする。名前の区画・文字の区画・辺のポートの並びが要る大きさより小さくはしない。本体の図の箱は持ち主の箱の幅いっぱいに広げるので、高さだけを詰める。
- 描く範囲が `perform` の行動のときは、`action` の形にし、名前の区画を `«perform action»` にする。図の中の `perform` の行動の箱には、引数も中の図も描かず、メンバーを文字の区画に出す。
- 行動の中の行動・継承・フローは、行動の箱の中に、同じアクションフローの図として描く。`entry`・`do`・`exit` と `then body`・`else body`・`loop body` の本体は、本体が行動・継承・フロー・結合を直接持つときだけ図にし、そうでなければ文字で書く。状態遷移ビューの `action` の箱の中は図にしない。図にしないメンバーは文字の区画に出す。
- 継承の線は、線を持つ図の種類で決める。アクションフローの図(アクションフロービューと、状態遷移ビューの中の本体の図)では `aflow-succession`(破線・開いた矢じり。ガードがあれば `[式]`)、状態遷移の図では `st-succession`(実線)とする。行動の中の `if g then x;` も `aflow-succession` で描き、`else` は `else-branch` で描く。フローはフローの線、結合は `binding-connection` で描く。始点・終点を省いた書き方の端は 7.8 節の規則で求め、求まらないものは描かず、図の診断に出す。
- 部品ごとの列(swimlane): 描く範囲の行動が直接持ち図に描いた行動を、外の部品の使用が `perform` するとき、その部品の列を作り、その行動を入れる。列の頭は、1 行目に `«performer»`、2 行目に部品の根の名前空間からの修飾名、その下に破線の区切りと斜体の見出し `perform actions` とし、列は破線の箱にする。列は縦の辺で互いに接し、上と下の辺をそろえる(8.2.3.17 節の注)。どの列にも入らない節点は列の外の左に置く。2 つ以上の部品が `perform` する行動は、記述の順で最初の部品の列に入れ、残りを図の診断に出す。列を作るのは一番外の図だけとする。
- 配置: アクションフローの図(アクションフロービューの図、行動の箱・本体の区画の中の図、状態遷移ビューの中の本体の図、`view` の図の最上位)は、流れの段で並べる。状態遷移ビューの状態の箱の中は、記述の順の格子(7.3 節)のままとする。
  - 段をたどる線は、継承(ガード付きのもの、行動の中の遷移を含む)、`else`、継承フローとする。フローと結合はたどらない。線の端がポート・引数・`proxy` なら持ち主の箱、入れ子の要素ならその祖先の、領域の要素に読み替える。両端が同じ要素になる線と、領域の外に出る線はたどらない。
  - 起点は開始の節点とする。なければ、入ってくる継承がなく出ていく継承がある要素を記述の順に起点とし、それもなければ(継承がすべて輪の中にあるとき)継承を持つ要素のうち最初に書いたものを起点とする。起点からの最短の段数を、その要素の段(行)とする。
  - 同じ段の要素は、記述の順で左から並べる。継承を持たない要素とたどり着けない要素は、最後の段の下に、記述の順の格子(1 行に ceil(√k) 個)で並べる。継承が 1 本もない領域は、すべてを格子に置く。
  - 行の間隔は 40 px を基本とし、自分自身に戻る線があるときはその分を広げる。箱は列の中央に置く。
  - 列(swimlane)があるときは、列と列の外の要素をまとめて段を求め、各列の中で段を行にする。行の高さは列どうしでそろえる。
  - 引数の辺: アクションフローの図の中の行動の箱(外側の箱を含む)の引数は、最初のフロー(フロー・継承フロー)の相手の箱がある側の辺に置く。相手が下の段なら下の辺、上の段なら上の辺、同じ段なら相手のいる左右の辺とする。相手が持ち主の箱の中にあるときなど、段と列で比べられないときは、向きのないポートと同じく相手の位置で決める。フローの相手がない引数は `in` を左、`out` を右に置く。向きの矢印は、`in` が内向き、`out` が外向き。
  - 線と文字の規則、線の端の仕上げは 7.3 節と同じとする。図の質の検査(10 章)も同じものを当てる。

### 7.6 シーケンスビュー

- シーケンスビューで描くのは、図表記文法の `sequence-view` から展開される生成規則のすべて(部品とポートの頭 `sq-part`・`sq-port`、生存線 `lifeline`、生存線の上の点 `sq-proxy`、メッセージ `message`、継承 `sq-succession`、注釈・依存)とする。描く範囲がオカレンスの定義・使用ならその箱の中に、部品の定義・使用なら `sequence` の区画(区切りの横線と斜体の見出し)の中に `sequence-view` を描く。参照のオカレンスの箱は破線とする。
- 頭: 描く範囲が直接持つ部品を頭にし、記述の順で図の上に横一列に並べる。範囲が直接持つポートも、頭として記述の順に並べる。入れ子の部品へのメッセージの端は、連鎖の最初の区切りの部品を頭にし、残りを点の文字に書く。参照の部品の頭も実線の箱で、名前の区画を `«ref part»` にする。
- ポートの頭: メッセージの端の連鎖が通るポートだけを、部品の頭の下の辺に小さな四角で付け、そこから生存線を下ろす。ポートを持つ部品の生存線は、頭の左の辺の近くに置く。
- 生存線は頭の下から伸びる破線とする。メッセージの端が `頭.事象` か頭そのもののときは点を描かず、生存線に着ける。頭の後ろが 2 区切り以上の端と、`sq-succession` の端には点(`sq-proxy`)を描き、残りの連鎖を `.` から始まる文字で書く。
- メッセージは、送り手と受け手の生存線の間の横向きの矢印とし、ラベルはメッセージの名前と運ぶものの型(相互接続ビューの `message` と同じ文字)とする。同じ生存線に戻るメッセージは、右へ出て下がって戻る形にする。メッセージの端を書かないときは、頭の中の事象の参照で、送り手(`sourceEvent`・`source`)と受け手(`targetEvent`・`target`)を求める。
- 縦の順: 頭の中の事象の間の継承と、メッセージの間の継承を順の関係とし、トポロジカルソートで上から並べる。順の決まらない組は記述の順とする。1 つの段に 1 本のメッセージを置く。頭をまたぐ事象の間の継承は `sq-succession`(破線)で描き、頭の中の継承とメッセージの間の継承は線に描かず順にだけ使う。範囲が直接持つメッセージの間の継承は `successions` の区画に文字で出す。
- 注釈先が頭 1 つの注は、その頭の上に置いて縦に短く結ぶ。それ以外の注と、頭の上の通り道を通るほかの線が残る領域の注は、頭の並びの右に置く。依存は、頭と注釈の記号の間のものだけを描く。
- 図の質: 生存線は (a) の障害物と (b) の線に入れない。メッセージ・継承が生存線を横切ることは (a) に数えない。
- 線と文字の規則、線の端の仕上げは 7.3 節と同じとする。

### 7.7 一般ビュー

- 分野ごとの記号(列挙・割り当て・計算・制約・要求・ケース・解析・検証・ユースケース・ビューと視点・メタデータ。SysML 2.0 の 8.2.3.8・8.2.3.15・8.2.3.19〜8.2.3.27 節):
  - ユースケースの定義は角の四角、使用は角の丸い四角とする(楕円にしない。8.2.3.25 節の図)。
  - 計算・制約・要求・解析・検証・ユースケースの定義と使用の引数(向きのある特徴。主体・行為者・利害関係者と戻り値を除く)は、相互接続ビューと同じく箱の辺の `param-*` に描く(`in` は左、`out` は右、`inout` と向きのないものは上)。戻り値と結果の式は `result` の区画に書く。箱の中のアクションフローの図・一般ビューの図は描かない。
  - `subject-actors-stakeholders-node` の選択肢の箱(要求の使用、解析・検証・ユースケースの定義と使用)が持つ主体・行為者・利害関係者は、節点(主体と利害関係者は小さな角の丸い四角、行為者は棒人間)にして、持ち主の箱と `distinguished-parameter-link`(矢じりのない実線)で結ぶ。選択肢にない箱(要求の定義など)では区画に書く。持ち主と節点を結ぶ線(関心事と利害関係者の `concern-stakeholder-link` を含む)は関係の段をたどる線に入れ(持ち主が上、節点が下)、節点は持ち主の 1 つ下の段に、段の中の並べ方で持ち主の近くに並ぶ。行為者の下の辺に着くことになる帯の線は、帯で引かずに経路の探索で引く。
  - 参照するだけの `satisfy`・`require`・`assume`・`frame`・`assert`・`verify`・`include`(宣言がキーワードと参照だけで、本体や型を持たないもの)と、端が 2 つの `allocate` は、両端が図にあれば、実線で終点に開いた矢じりの線にし、今の箱・区画の行を描かない。両端が図になければ、箱か区画の行のままとする。宣言するもの(`require constraint x { … }` など)と、`not` 付きのものは、箱か区画の行のままとする。`satisfy R by x;` は x(`by` がなければ持ち主)から R へ、`verify` は検証の箱から要求へ引く。
  - 図の中の view の箱が持つ `expose` は、公開した要素が同じ図に箱として描かれていれば、view の箱からその箱へ破線(`«expose»`・`«expose»*`・`«expose»**`)にし、exposes の区画の行から除く。
  - 線の文字は、キーワード(`«satisfy»` など)の後ろに、使用が宣言した名前・型を書く(7.8 節)。
  - これらの新しい線は、関係の段をたどる線に入れない。
  - メタデータは注釈の記号と注釈の線、列挙の値は `enums` の区画とする(GR4 からの記号)。
- 描くもの: 図表記文法の `general-view` のうち、次のもの。
  - パッケージ(`package-node`)と import(`import`・`top-level-import`・`recursive-import`)。描く範囲のパッケージは外枠にしてメンバーを中に置き、所属の線と `«alias»` の箱は描かない。入れ子のパッケージは名前だけを描く。`view` の図で、図に描くパッケージが図に描くメンバーを持つとき(`expose X::**` で X とメンバーを公開したときなど)は、そのパッケージを外枠と同じ形の箱にし、メンバーを箱の中に同じ規則で描く。メンバーを入れる箱は、持ち主が描くパッケージならそれ、そうでなければ公開の経由(import で取り込んだメンバーなど)の描くパッケージとする。箱の外のものとの線は、箱の縁をまたいで引く。この箱には左下の `...` を付けず、文字の区画も描かない。名前空間の import は破線のパッケージ、要素 1 つの import は図の診断に出す。import の線の文字の可視性は `private`・`protected` のときだけ書く。
  - 定義と使用の箱(`definition-node`・`usage-node`)。これまでのビューで作った記号(部品・ポート・項目・属性・接続・インターフェース・行動・状態・オカレンスなど)はそのまま使う。
  - 型の関係(`subclassification`・`definition`・`subsetting`・`reference-subsetting`・`redefinition`・`composite-feature-membership`・`noncomposite-feature-membership`)と、依存・注釈。上位・型・持ち主・取り込まれる側を線の終点にし、端の記号を終点に描く。
- 箱にする使用と区画に出す使用: 属性・ポート、向きのある特徴と引数、線になる使用、参照する使用、`variant` は、持ち主の箱の文字の区画に出す。ほかの使用は、深さによらず箱にし、持ち主から合成の線(参照の使用・端・事象は `noncomposite-feature-membership`)で、使用からその型の定義へ型付けの線(`definition`)で結ぶ。`exhibit state` は持ち主の箱の `exhibit states` の区画に出す。
- `view` の `expose` で公開した属性・ポートは、持ち主の箱が図にあればその区画に出す。持ち主(定義か使用)が描く範囲の外にある特徴は、箱にして図の下にまとめて置き、図の診断(`owner-out-of-scope`)に件数と名前を出す。
- 描く範囲のパッケージが直接持つ要素を描く。根の名前空間は、パッケージ以外の要素を直接持つときだけ候補にする。線の相手が描く範囲の外にあるときは、その線を描かず、図の診断に出す。本文の図表記に節点のない種類は描かず、図の診断(`not-drawn`)に出す(箱の中では区画に出す)。
- 配置:
  - 関係の段で上から下へ並べる。特殊化では上位を上、合成では持ち主を上、型付けでは使用を上・定義を下にする。起点と段の求め方はアクションフローの図の段(7.5 節)と同じとし、輪になる関係と逆の向きを求める関係は、最短の段数で決まる段に置いて上向きの線で引く。関係を持たない要素は、最後の段の下に記述の順の格子で並べる。
  - 段の折り返し: 行の要素がすでに ceil(√n) 個(n は領域の要素の数)あり、次の要素を足すと箱の幅と間隔の合計が 2400 px を超えるときだけ、次の要素を次の行へ移す(折り返した行は同じ段の続きとして、次の段より上に置く)。
  - 同じ段の中の並びは、つながる線の相手の位置の平均で並べ直す(重心法。上から下・下から上へ数回ずつ。順の決まらない組は記述の順)。型付けの相手の定義は、できるだけ使用の真下に寄せる。
- 線:
  - 段に並べた要素どうしの線は、線の本数によらず、段と段の間の帯で引く。同じ段どうしの線は、両方の箱の下の辺を使い、下の帯を通す。帯の余白は 32 px、レーンの間隔は 12 px、通り道の余白は 16 px、辺の上の着く点の間隔は 18 px 以上(足りなければ箱の幅を広げる)とする。段を 2 つ以上またぐ線は、間の段の箱の隙間のうち、曲がりと長さの少ないものを通る。両端が向かい合う辺(下の辺と上の辺)にあり、2 つの辺の横の範囲が重なる線は、着く点の間隔の規則を守れるときだけ、両端の着く点を同じ横の位置にそろえてまっすぐ通す。帯で引いた線には、線の端の仕上げ(7.3 節)を当てない。
  - 帯の中の線の上下の順は、制約を守る範囲で、帯の中の交差が減るように 1 本ずつ動かす。動かした図は、動かさない図と比べて、図の (g) が減り (a)〜(e) が増えないときだけ採る。
  - 帯のレーンの制約が輪になるときは、着く点をずらして、2 本の線を重ねない(重なりのかわりに交差になることがある)。
  - これらの線の直しは、`src/view/index.js` の定数 `BEND` の 1 か所で切れる。切れば GR10 の終わりの図に戻る。
  - 注が相手の箱の中にある注釈の線は、探索をせず、囲む箱の内側の最も近い縁へ直線で引く(当たるときは 1 回だけ曲げる)。
  - ほかの線(区画の行・枠・図に着く線など)は、7.3 節の規則で引く。
- 当たり判定は 7.3 節と同じとする。図の質の検査(10 章)も同じものを当てる。
- 標準ライブラリのような、メンバーの多いパッケージでも、1 候補 2.5 秒以内で描き終える(作業の機械での実測。単独のプロセスで、プロセスの最初の描画(準備の時間を含む)を除いて測り、最初の描画の値も記録する)。線の本数の上限は設けない。

## 8. 図からの編集

段階 3 までを目標とする。相互接続ビューの「テキスト → 図」と名前解決を固めてから、段階 1、2、3 の順に足す。

| 段階 | 図でできること | テキストの書き換え |
|---|---|---|
| 0 | 図の要素をクリックすると、テキストの該当箇所に移る | なし |
| 1 | 名前や型などの文字を直す | 名前と、それを参照している箇所を置き換える |
| 2 | 部品・ポート・接続を追加する | 該当箇所に宣言を足す |
| 3 | 要素を削除する | 宣言を消し、それを参照している箇所も直す |

- 書き換えは、構文木の範囲に限る。利用者のコメント・改行・記述の順を保つ。
- すでにある要素を指す名前を書き足すとき(追加の型・接続の端、`view` の範囲など)は、その要素の宣言の書き方に合わせる(宣言が `'D8'` なら `'D8'`)。宣言のない名前と新しい名前は、段階 1 の引用符の規則で書く。
- その操作で書き換える参照と、書き換える名前を参照しうる箇所に、解決できないもの(標準ライブラリへの参照で未検査のものなど)や曖昧なものが 1 つでもあれば、その操作を実行せず、理由を表示する。D3 の印の付いた参照(6.2 節)も、ここでは未検査と同じに扱う。それ以外の箇所の未検査は、操作を妨げない。
- 書き換えた後のテキストを解析し直し、モデルの差分が意図した変更だけであることを確かめる。満たさなければ、書き換え前に戻す。
- 編集は取り消せるようにする。
- 書き換えた後は、名前の変更では変えた要素を、追加では足した要素を、削除では持ち主を選んだ状態にする。
- フォルダを開いているとき(9.4 節)は、書き換える箇所が複数のファイルにまたがる操作も行う(9.4 節の段階 B)。前の検査と後の確かめは全ファイルで行い、1 回の操作を 1 回の取り消しで、すべてのファイルについて戻す。書き換えた後は、選んだ要素のあるファイルを表示する。

段階 1(名前の変更)の規則:

- 操作: 図で要素を選ぶと、編集欄にその要素の名前と短い名前(`<…>`)を出す。どちらかを書き換えて確定すると、書き換えを行う。対象は、利用者のモデルの中で名前(または短い名前)を宣言した要素とする。宣言していない要素(暗黙の要素、名前を受け継ぐだけの再定義など)、内蔵する表の項目、未検査の参照の先は、操作を受け付けず、理由を表示する。
- 書き換える箇所: 宣言の名前(短い名前を変えたときは短い名前)と、その要素に解決したすべての参照(逆引き。修飾名の途中の区切りと特徴の連鎖の途中の区切りを含む)のうち、変えた方の名前で書かれた区切りだけ。名前を宣言せず、実効の名前(KerML 1.0 の `effectiveName`)を別の要素から受け継ぐ要素(名前を書かない再定義 `port :>> x { … }`、`variant`、`perform` など)で、受け継ぎを何段たどっても元がその要素であるものは、その要素と一緒に名前が変わるので、それに解決した参照のうち同じ名前で書かれた区切りも書き換える。別名(`alias A for X`)の名前 A で書いた参照は変えず、`for X` の参照は変える。
- 引用符: 新しい名前だけで決める。英字か `_` で始まり英数字と `_` だけからなり、キーワードでない名前は引用符なしで書き、それ以外(日本語を含むもの、空白を含むもの、キーワードと同じもの)は `'…'` で囲み、本文の字句の規則どおりに `'` と `\` をエスケープする。宣言と参照のすべてで同じ書き方にする。空の名前は受け付けない。
- 拒否する条件: 8 章の上の規則に加えて、新しい名前が同じ名前空間のほかのメンバーと区別できなくなるとき(9.2 節の S2 と同じ判定)。判定は、名前を変える要素と同じ名前空間のほかのメンバーの組ごとに行い、意味エラーの件数の増減では判定しない(すでに S2 のある名前空間でも、新しい名前がほかのメンバーと区別できなければ拒否する)。上の規則の「書き換える名前を参照しうる箇所」は、書かれた区切りの名前が、前の名前か新しい名前と同じ参照とする。
- 確かめ: 書き換えた後のテキストを解析し直し、構文エラーがないこと、意味エラーと未検査の件数が増えないこと、書き換える前にその要素に解決していた参照がすべて同じ要素に解決すること、ほかの参照の状態と解決先が変わらないこと、モデルの差分がその要素の名前(と、それを含む修飾名)だけであることを確かめる。満たさなければ書き換える前に戻し、理由を表示する。
- 取り消し: 1 回の名前の変更を、テキスト欄の取り消し(Ctrl+Z)の 1 回で戻せるようにする。書き換えた箇所の外の、利用者のコメント・改行・字下げは変えない。

段階 2(追加)の規則:

- 操作: 図で要素を選ぶと、編集欄に、その要素に足せるものの操作を出す。
  - 部品を足す: 選んだものが部品の定義・使用(一般ビューではパッケージも)のとき。名前(必須)と型(利用者のモデルの部品の定義から選ぶ。なしも可)を入れ、`part 名前 : 型;` を足す。
  - ポートを足す: 選んだものが部品の定義・使用のとき。名前(必須)、型(利用者のモデルのポートの定義から選ぶ。なしも可。共役 `~` を選べる)、向き(なし・`in`・`out`・`inout`)を入れ、`向き port 名前 : 型;` を足す。
  - 接続を足す: 相互接続ビューで「接続を足す」を押し、図のポート(または部品)を 2 つ順に選ぶ。形は `connect 端1 to 端2;` を既定とし、利用者のモデルにインターフェースの定義があれば、それを選んで `interface 名前 : 型 connect 端1 to 端2;` にできる(名前はなしも可)。
- 書き足す場所: 部品とポートは、選んだものの本体の最後のメンバーの後ろ。接続は、2 つの端をともに入れ子に持つ最も内側の部品の定義・使用(描く範囲の外側の箱を含む)の本体の最後のメンバーの後ろ。端は、その場所から名前で指す特徴の連鎖(`a.p`)で書く。字下げは本体の最後のメンバーに合わせ、メンバーがなければ持ち主の字下げに 4 つの空白を足す。持ち主に本体がない(`;` で終わる)ときは、`;` を `{`・改行・足すもの・改行・持ち主の字下げの `}` に書き換える。
- 名前の引用符は段階 1 と同じ規則とする。同じ名前空間のほかのメンバーと区別できない名前(S2)は拒否する。
- 拒否する条件: 8 章の上の規則(書き足す参照に未検査・曖昧・D3 の印のものがある)、S2、名前で指せない端(名前のない要素を通る、など)。
- 確かめ: 書き足した後のテキストを解析し直し、構文エラーがないこと、意味エラーと未検査の件数が増えないこと、書き足す前の参照の状態と解決先が変わらないこと、モデルの差分が足した要素(とその参照)だけであること、接続の端が選んだポート(または部品)に解決することを確かめる。満たさなければ書き足す前に戻し、理由を表示する。
- 取り消し: 1 回の追加を、テキスト欄の Ctrl+Z の 1 回で戻せるようにする。

段階 3(削除)の規則:

- 操作: 図で要素を選び、編集欄の「削除」を押す。対象は、利用者のモデルの中で宣言した要素とする(内蔵する表の項目、暗黙の要素は受け付けない)。
- 一緒に消すもの: 端(特徴の連鎖の途中を含む)が、消す要素かその中のものに解決する、接続・インターフェース・フロー・結合・継承の宣言(消す要素の外にあるもの)。始点を省いた `then X` と終点を省いた `then action x` の形の継承で、省いた始点・終点(7.8 節)が消す要素になるものも、一緒に消す。
- 拒否する条件: 8 章の上の規則(消す名前を参照しうる箇所に未検査・曖昧・D3 の印のものがある)に加えて、消す要素とその中のものに解決する参照が、消す範囲(消す要素と一緒に消すもの)の外に残るとき(型付け・特殊化・再定義・`expose`・`satisfy`・`import`・式の中の参照など)。残る参照の箇所(行と列)を一覧で出す。参照でない暗黙のつながりが残るときも拒否し、その箇所を一覧で出す:
  - 消す要素が、消す範囲の外の遷移の省いた始点(7.8 節の規則で求めるもの。`if … then` など)になっているとき。
  - 消す範囲の外の特徴が、消す要素を暗黙に再定義している(6.2 節の暗黙の再定義。位置による端・引数の再定義を含む)とき。
  - 端か引数を消すと、同じ持ち主の後ろの端・引数の位置がずれ、それらの暗黙の再定義の相手が変わるとき。
- 消す前の確認: 編集欄に、消す要素と一緒に消すものの一覧を出し、利用者が「消す」を押したときだけ消す。
- 消し方: 宣言の範囲を消す。宣言がある行にほかの文がなければ、その行ごと(字下げと改行を含めて)消す。宣言の直前の行の注(`//`・`//*`)は消さない。
- 確かめ: 消した後のテキストを解析し直し、構文エラーがないこと、意味エラーの件数が増えないこと、残った参照の状態と解決先が変わらないこと、モデルの差分が消した要素とその中身と一緒に消したものだけであることを確かめる。満たさなければ消す前に戻し、理由を表示する。
- 取り消し: 1 回の削除を、テキスト欄の Ctrl+Z の 1 回で戻せるようにする。

- 「ビュー」の選択欄の順は、SysML 2.0 の 9.2.20.1 節の表 34 の順に、一般・相互接続・アクションフロー・状態遷移・シーケンス・グリッドビューとする。

- テキストに構文エラーがある間は、最後に正しく描けた図を薄く表示し、図からの編集を止める。
- 「書き方」はダイアログで開き、枠外をクリックすると閉じる。書き方には、作ったビューごとに描くための書き方の短い例(状態遷移ビューでは状態・遷移・`accept`・`if`・`do`・`entry`・`exit`・`exhibit state`)と、生成 AI に書かせるときの指示文の例を載せる。
- ファイルは「開く」とドラッグ・アンド・ドロップで読み込む。2 つ以上のファイル・フォルダを一度にドロップしたときは、どれも読み込まずに、1 つのファイルかフォルダを 1 つだけドロップするよう理由を表示する。テキストを、ページを開いた・ファイルを開いた・保存した・「新規」・「例を読み込む」の後に書き換えていたら(貼り付けを含む)、「開く」「フォルダを開く」「新規」「例を読み込む」とドロップで、置き換えの確認を出す。書き換えていなければ、確認を出さずに置き換える(フォルダのときの 9.4 節の規則と同じ条件)。やめたときは今のテキストを保つ。
- 置き換えの確認が要る状態(書き換えたまま保存していないもの。フォルダのときは 9.4 節の条件)で、ページを閉じる・読み直すときは、ブラウザの確認(`beforeunload`)を出す。
- 「新規」は、空のパッケージの骨組み(`package '新しいシステム' {` と `}` の 2 行)を入れる。一般ビューでその外枠を選べば「部品を足す」から始められる。
- 「例を読み込む」では、入門用の短い例と、今の機能紹介用の例の 2 つから選ぶ。入門用の例は、部品の定義・使用・ポート・接続・`view` だけを使う小さなもの(電池・スイッチ・ランプ程度)とし、意味エラー・警告・未検査が 0 件であること。
- テキスト欄の空のときの案内は、特定のビューに依らない文(選んだビューの図が右に出ること)にする。

フローチャートにない操作として、ビューの切り替えと、描く範囲の候補の選択(上の帯の「ビュー」と「範囲」)、範囲を `view` として書き足すボタン(「範囲」の選択欄の右の「view を書き足す」。5 章。範囲が `view` のときは押せない)を加える。

### 9.2 診断

- 構文エラー、意味エラー、警告、未検査、内部エラーを分けて表示する。内部エラーのときに、範囲の欄などに「構文エラー」と出さない。未検査を正常として表示しない。診断は、生成 AI に渡す修正依頼としてコピーできるようにする。修正依頼の文に入る診断が 1 件もないときは、「修正依頼をコピー」を押せなくする(診断欄に出るのが、修正依頼の文に入れない図の診断(描く範囲の候補がないなどの案内)だけのときを含む)。修正依頼では、構文エラー・意味エラーは直すものとし、警告は意図の確認事項として扱わせる(書き間違いと判断できるものだけ直し、判断できないものは変えずに、確かめたいことを質問として挙げる)。
- D3 の印の付いた参照(6.2 節)は、診断では解決済みとして表示する。
- 図の診断として、描いていない要素(ほかのビューの要素、描く範囲の外に端のある接続、端が求まらないか図にない遷移・継承)、反映していない `filter`・`render`、`expose X;` で中が空の箱への案内(5 章)を出す。
- 未検査は、件数と、名前ごとにまとめた一覧で出す。意味エラーにした参照は、未検査に数えない。
- 意味エラーは、本文の規範に反することが、このアプリの持つ情報だけで確かめられるものに限る。標準ライブラリがないと判定できない場合は判定せず、意味エラーにしない。
- 意味エラーとして検査するのは、次の項目とする。

| 番号 | 項目 | 本文の根拠 | 判定の条件 |
|---|---|---|---|
| S1 | 名前が解決できない | KerML 1.0 の 8.2.3.5.1 節 | 解決できず、しかも探した経路のどの名前空間も、暗黙の特殊化・対象のわからない import・評価できないフィルター条件を持たないとき。大域の名前空間は標準ライブラリを含むので、単純な名前、修飾名の最初の区切り、`$::` の後の最初の区切りは、大域の名前空間に見つからなくても S1 にしない |
| S2 | 区別できないメンバー | KerML 1.0 の 8.3.2.4.5 節 `validateNamespaceDistinguishibility`、8.3.2.4.3 節 `isDistinguishableFrom` | 名前空間ごとに、本文の「区別できる」の定義で判定する。名前が同じでも、要素の種類が互いに適合しなければ区別できる。名前解決の「曖昧」(6.2 節)からは判定しない。継承や import の先がライブラリの要素なら、その部分は判定しない。import で取り込んだもの同士や、所有するものと区別できない取り込みは、取り込まれないと読み(KerML 1.0 の 8.3.2.4.5 節 `importedMemberships` の説明)、S2 にしない |
| S3 | 解決した要素の種類が文脈に合わない | KerML 1.0 の 8.2.3.5.1 節 | 解決先が利用者のモデルの要素か内蔵する表の項目で、文脈で期待される種類(抽象構文の属性の型)に適合しないとき |
| S4 | 根の名前空間の import が `private` でない | KerML 1.0 の 8.3.2.4.2 節 `validateImportTopLevelVisibility` | 根の名前空間が所有する import が `public` か `protected` のとき。本文の文法では import の可視性は省けない(省くと構文エラー) |
| T1 | 型が共役を 2 つ以上持つ | KerML 1.0 の 8.3.3.1.10 節 `validateTypeAtMostOneConjugator` | 型が所有する共役の関係が 2 つ以上のとき。この形は KerML の式の本体の中でしか書けない |
| T2 | 再定義の向きが合わない | KerML 1.0 の 8.3.3.3.8 節 `validateRedefinitionDirectionConformance` | 再定義される特徴の向きを、再定義する特徴を持つ型から見た向きとして、本文の `directionOf`(8.3.3.1.10 節。上位の型をたどり、共役の型を通るたびに `in` と `out` を入れ替える)で求める。その向きが `in`・`out` で再定義する特徴の向きと違うとき、または `inout` で再定義する特徴が向きを持たないとき。明示の再定義、特殊化した定義の中の再定義、暗黙の再定義(6.2 節)のすべてが対象。たどる経路が未検査の要素に出たら判定しない。呼び出しの式の引数(名前付きの引数を含む)は判定しない(本文の文法では向きを持たず、制約 `validateParameterMembershipParameterDirection` と食い違うため)。フローの端の特徴は判定しない(向きは再定義される特徴に合わせて決まる。KerML 1.0 の 8.2.5.9.2 節) |
| T3 | 端の特徴を再定義する特徴が端でない | KerML 1.0 の 8.3.3.3.8 節 `validateRedefinitionEndConformance` | 再定義される特徴が利用者のモデルの端の特徴で、再定義する特徴が端でないとき |
| U1 | 変種(`variant`)の持ち主が変化点でない | SysML 2.0 の 8.3.6.5 節 `validateVariantMembershipOwningNamespace` | `variant` を所有する定義・使用が `variation` でないとき |
| U4 | ポートの中に合成の特徴がある | SysML 2.0 の 8.3.12.5 節 `validatePortDefinitionOwnedUsagesNotComposite`、8.3.12.6 節 `validatePortUsageNestedUsagesNotComposite` | ポートの定義・使用が所有する、ポートでない使用が合成のとき。参照かどうかは本文どおりに求める(向きのある使用・端・属性・参照の使用など、常に参照になるものを含む) |
| U5 | 並行状態の中の状態に遷移がある | SysML 2.0 の 8.3.18.6 節 `validateStateUsageParallelSubactions` | `parallel` の状態の、入れ子のアクション・状態を始点か終点とする遷移があるとき。始点・終点が解決済みのものだけで判定する |
| U6 | 状態でない始点の遷移が引き金を持つ | SysML 2.0 の 8.3.18.9 節 `validateTransitionUsageTriggerActions` | 遷移の始点が利用者のモデルの要素で `StateUsage` に適合せず、遷移が引き金(`accept`)を持つとき。内蔵する表の項目(`start` など)に解決した始点は、標準ライブラリで状態に再定義されうるので判定しない |

- 次の 3 つは検査しない。
  - 属性の中に合成の特徴があること(SysML 2.0 の 8.3.7.2 節 `validateAttributeDefinitionFeatures`、8.3.7.3 節 `validateAttributeUsageFeatures`)。属性の中の特徴が書き方によらず参照になるのか、利用者に課す制約なのかが本文で読み分けられず、パイロット実装も KerML の合成の意味の課題(KERML-4)が解決するまで検査を見送っているため。
  - 多重度の範囲が負であること(KerML 1.0 の 8.3.4.11.2 節 `validateMultiplicityRangeBoundResultTypes`)。本文の文法では多重度の境界に単項のマイナスを書けず(数などの字句か特徴の参照だけ)、特徴の参照の値をたどる評価は誤検出の危険があるため。
  - 部品の型に部品の定義がないこと(SysML 2.0 の 8.3.11.3 節 `validatePartUsagePartDefinition`)。部品の使用は必ず `Parts::parts` を特殊化し(8.3.11.3 節 `checkPartUsageSpecialization`)、特徴の型には部分集合にした特徴の型も入る(KerML 1.0 の 8.3.3.3.4 節 `deriveFeatureType`)ので、本文どおりなら発火しないと読む。パイロット実装もこの検査を持たない。
- 意味エラーは、構文エラーと同じく、行と列を付けて診断に出し、クリックするとテキストの該当箇所に移る。構文エラーのクリックでは、行と列の位置の字句を選ぶ(行全体を選ばない)。診断のクリックで移るときは、選んだ字句がテキスト欄の見える範囲に入るよう、縦と横に送る(9.5 節の移動と同じ)。
- 警告: 書き間違いのおそれがあり、利用者に意図を確かめてほしい書き方を、意味エラーとは別に「警告」として出す。警告は、規範の制約に反するかどうかを述べない(W1 の出典の 7 章は参考の章で、8 章の検査規則に同じ制約があるかは確かめていない)。そのため、警告の見出しと文は、誤りや禁止と断定せず、意図した書き方かを確かめるよう促す形にする(見出しの例: 「警告(書き間違いのおそれがあるため、意図を確かめてほしい箇所)」)。警告は図を止めず、件数を別に数え、行と列を付けて診断に出し(クリックで該当箇所に移る)、修正依頼のコピーにも含める。項目ごとに出典(本文の箇所か、このアプリの「書き方」の決まり)を示す。種類の日本語名は「書き方」の言葉にそろえる(`action def` は「行動の定義」)。警告にするのは次の項目とする。

| 番号 | 項目 | 出典 | 判定の条件 |
|---|---|---|---|
| W1 | 使用の型が、その種類の使用に許される定義の種類でない(例: `action def A; part p : A;`) | SysML 2.0 の 7 章の各節の「… usage must (may) only be defined by …」の記述(例: 7.11.2 節 部品は項目の定義(部品の定義を含む)か KerML の構造)と、要求・ケースの actor・stakeholder の記述(7.21.2 節・7.22.2 節。部品の定義) | 使用が書いた型(明示の型付け `:`)のうち、利用者のモデルの要素か標準ライブラリの索引の要素に解決したものが、7 章でその使用の種類に許される定義の種類(下位の種類を含む)のどれにも適合しないとき。7 章に記述のある使用の種類だけを対象にする(対象の一覧と出典の行は `grammar/` の表に持つ)。actor・stakeholder として宣言した部品の使用は、その記述(部品の定義)で判定する。未検査・曖昧の型は判定しない。W2 に当たる型付けは判定しない(同じ箇所に W2 を出す) |
| W2 | 使用の名前が、型に書いた名前と同じ(例: `part 'ブザー' : 'ブザー';`) | このアプリの「書き方」と生成 AI 向けプロンプトの決まり(部品とポートの使用の名前を定義の名前と別にする) | 部品とポートの使用で、宣言した名前が、明示の型付けに書いた型の名前(修飾名なら最後の区切り。引用符を外して比べる)と同じとき。型の名前の解決の結果(解決・未検査・曖昧、解決先が定義か使用か)によらず、書かれたテキストで判定する(同じ名前にすると、型の名前が曖昧になったり、使用そのものに解決したりして、解決の結果からは判定できないため) |


### 9.3 保存形式

| 形式 | 扱い |
|---|---|
| `.sysml` | 正本。テキストをそのまま保存する。アプリ固有の情報を書き込まない。開いたファイルの改行の形(LF・CR LF・CR)を覚えておき、保存のときにその形で書く(テキスト欄の中では LF で扱う)。「新規」と貼り付けたテキストは LF とする |
| `.svg` | 図・表 1 つずつの画像。出力のみ。テキスト(原文)は埋め込まない |
| `.png` | 図・表 1 つずつの画像(2 倍の解像度)。出力のみ |
| PDF | 図・表 1 つずつを、同じ大きさの紙(余白 0)でブラウザの印刷にかける。印刷の画面の「PDF に保存」で、ベクター形式の PDF 1 ページになる。アプリの中で PDF のファイルは作らない |
| タブ区切りの文字 | 表をクリップボードに写す(表計算ソフトや Word の表に貼れる)。ファイルにはしない。`=`・`+`・`-`・`@` で始まるセルは、表計算ソフトで式として評価されないよう、先頭に `'` を付ける。`"` で始まるセルも、表計算ソフトが引用の始まりとして読み、後ろのセルとつなげないよう、先頭に `'` を付ける |

- 正本は `.sysml` だけとする。SVG にテキストを埋め込まない(正本が 2 つになり、版の管理が分かりにくくなるため)。
- 「開く」で受け付けるのは `.sysml` だけとする。
- 保存する SVG には、紙の大きさの指定(`<style>@page{size:幅px 高さpx;margin:0}</style>`)を入れる。画面の操作のための印(`data-*` と当たり判定)は入れない。表の SVG・PNG・PDF には題を入れず、図には左上の名前のタブを入れる。
- ファイル名は、図は「元の名前_ビュー_範囲の名前」、表は「元の名前_grid_表の題」とする(`grid` はグリッドビューの値)(ファイル名に使えない文字と空白は「_」にする)。
- 拡張子 `.sysml` は、SysML 2.0 の 2 章(適合性)のモデル交換の項で、`.kpar` 内のテキスト表記ファイルに定められた拡張子に合わせる。

### 9.4 フォルダ単位の読み込みと保存

大きなシステムをファイルに分けて書けるよう、フォルダの中の `.sysml` をまとめて 1 つのモデルとして扱う。SysML v2 では、ファイルごとの根の名前空間の要素が大域の名前空間に入り、ほかのファイルから名前や import で参照できる(名前解決の規則は 6.2 節)。今の 1 ファイルの扱い(「開く」「新規」「例を読み込む」)は、そのまま残す。

3 つの段階に分けて作る。

| 段階 | 行うこと |
|---|---|
| A | フォルダの読み込み、全ファイルをまとめた解析・名前解決・意味エラー・警告・描画、ファイルごとの編集、1 つのファイルに収まる図からの編集 |
| B | フォルダへの上書き保存(Chrome・Edge)、ほかのブラウザでのフォルダの zip の保存、複数のファイルにまたがる図からの編集 |
| C | フォルダの木(エクスプローラー)と、ファイル・フォルダの操作(新しいファイル・新しいフォルダ・名前の変更・削除・移動・切り取り・コピー・貼り付け・再読み込み) |

段階 A の規則:

- 読み込み: 上の帯に「フォルダを開く」を足す。Chrome・Edge ではフォルダを選ぶ画面(File System Access API の `showDirectoryPicker`)で選び、選んだフォルダの扱い(ハンドル)をページを開いている間だけ覚える(段階 B の上書き保存に使う)。ほかのブラウザでは、フォルダを選ぶ欄(`webkitdirectory`)で読み込む。フォルダのドラッグ・アンド・ドロップでも読み込む。
- 読み込むファイル: フォルダの中の `.sysml` を、下のフォルダも含めてすべて読む。名前が `.` で始まるフォルダ(`.git` など)の中は読まない。ほかの拡張子のファイルは、解析には使わず、フォルダの木に名前だけを出す(段階 C)。ファイルはフォルダからの相対パス(区切りは `/`)で呼び、解析の並びは `.sysml` の相対パスの符号位置の順とする。`.sysml` が 1 つもないフォルダも開く(フォルダの木から新しいファイルを作れるようにするため)。
- 解析: すべてのファイルをまとめて 1 つのモデルとして解析する(ファイルごとに根の名前空間を作る。6.2 節)。構文エラーのあるファイルがあっても、ほかのファイルは解析する。ただし図からの編集は、どれかのファイルに構文エラーがある間は止める(9.1 節の今の規則を、全ファイルに当てる)。
- 画面: テキスト欄の左にフォルダの木(段階 C)を置き、テキスト欄の上に今のファイルの相対パスを出す。テキスト欄には木で選んだファイルを出す。ファイルごとに書き換えと取り消し(Ctrl+Z)の履歴を保つ(ファイルを切り替えても、ほかのファイルを書き換えても、前のファイルの取り消しの履歴を失わない)。ブラウザのテキスト欄の取り消しでは、ほかのファイルを書き換えた後に前のファイルの取り消しが効かないことを Chromium で確かめたので、フォルダを開いているときは、アプリが取り消しとやり直しの履歴をファイルごとに持つ(下の「取り消しの履歴」)。1 ファイルの扱いでは、今のままブラウザの取り消しを使う。
- 描く範囲の候補は、全ファイルの要素から 5 章の規則で作り、記述の順はファイルの並びの順、ファイルの中は記述の順とする。「範囲」の欄で表示が同じになる候補が 2 つ以上あるとき(別のファイルの同じ名前のパッケージなど)は、その候補の表示の後ろに「(相対パス)」を付ける(相対パスでも同じになるときは行も付ける)。図の要素をクリックすると、その要素のあるファイルに切り替えて該当箇所に移る。
- 診断: 診断ごとに、ファイルの相対パス・行・列を付ける。行と列は、そのファイルの中のものとする。クリックすると、そのファイルに切り替えて、そのファイルの中の行と列の該当箇所に移る(行だけを持つ診断(構文エラー・曖昧・未検査・図の診断)も、範囲を持つ診断(意味エラー・警告)も同じ)。修正依頼のコピーでは、診断ごとに相対パスを付け、テキストを含めるときは、診断のあるファイルだけを、相対パスの見出しを付けて含める。
- `view` を書き足すコマンド(5 章)は、範囲の要素のあるファイルに書き足す。
- 保存: 「保存」は、段階 B の規則(上書き保存か zip の保存)による。図・表の画像のファイル名の「元の名前」は、フォルダの名前とする。
- 置き換えの確認: どれかのファイルを書き換えていたら、「ディスクにない」の印のファイル(段階 C の再読み込み)が残っていたら(取り消しで書き換えの印が消えていても)、またはハンドルがないとき(段階 C)に、保存の zip に入れていない木の操作(作る・名前の変更・削除・移動・コピー)をしていたら、「開く」「フォルダを開く」「新規」「例を読み込む」とドロップで、置き換えの確認を出す(9.1 節と同じ)。「開く」「新規」「例を読み込む」を行うと、フォルダを閉じて 1 ファイルの扱いに戻る。

- 取り消しの履歴(フォルダを開いているとき): アプリがファイルごとに、取り消しとやり直しの履歴を持つ。
  - テキスト欄の Ctrl+Z を取り消し、Ctrl+Y と Ctrl+Shift+Z をやり直しとする。テキスト欄の右クリックの「元に戻す」「やり直し」も同じ履歴を使う。
  - 手で打った文字は、続けて打った文字を 1 つの履歴にまとめる。改行・カーソルの移動・貼り付け・切り取り・ほかのファイルへの切り替え・図からの編集で、まとまりを切る。図からの編集と `view` の書き足しは、1 回の操作を 1 つの履歴とする。
  - 日本語の変換中(`compositionstart` から `compositionend` まで)に、取り消し・やり直し(キー操作か、右クリックの「元に戻す」「やり直し」の `historyUndo`・`historyRedo`)が来たときは、何もしない(ブラウザの取り消しも止める)。変換中の印は、`compositionend` のほか、テキスト欄からフォーカスが外れたときと、ほかのファイルへの切り替えでも解く(印が残って履歴が止まらないようにする)。
  - 取り消しとやり直しの後は、カーソルを書き換えた箇所に置き、解析し直す。書き換えの印は、保存したときのテキストと同じかどうかで決める(取り消して保存したときの形に戻れば、印を消す)。
  - 複数のファイルにまたがる 1 回の操作(段階 B)は、書き換えたすべてのファイルの履歴に、つながった 1 つの履歴として入れる。どのファイルで取り消しても、すべてのファイルで戻す。ただし、そのうちのどれかのファイルで後から書き換えていて、その履歴が一番上にないときは、取り消さずに「ほかのファイル(相対パス)で後から書き換えたので、この操作は戻せません。先にそのファイルで取り消してください」の形の理由を表示する。やり直しも同じ。
  - つながった履歴が 1 つのファイルの履歴から消えたとき(上限を超えて古いものを捨てたとき、新しく書き換えてやり直しの履歴を消したとき)は、つながったほかのファイルの履歴からも、その操作と、それに続くもの(取り消しの履歴ではそれより古いもの、やり直しの履歴ではそれより後の操作)を消す。戻せない操作を履歴に残して、取り消し・やり直しが詰まることのないようにするため。このとき理由は表示しない(1 つのファイルで新しく書き換えるとやり直しの履歴が消えるのと同じ扱い)。
- 「書き方」に、パッケージに標準ライブラリの根の名前空間と同じ名前(`Parts`・`Items`・`Ports` など)を付けないことを書く(ほかのファイルから指すと曖昧になる。2.5 節)。

段階 B の規則:

- 上書き保存(Chrome・Edge): フォルダのハンドル(フォルダを選ぶ画面か、ドロップの `getAsFileSystemHandle` で得たもの)があるとき、「保存」で、書き換えたファイルだけを、読み込んだフォルダの同じ相対パスに書く。書き換えていないファイルは書かない(git などで管理したフォルダで、差分を書き換えたファイルだけにするため)。改行の形は、ファイルごとに読み込んだときの形を保つ(9.3 節)。書き込みの許可は、最初の上書き保存のときにブラウザの確認で求める。書けなかったファイルがあれば、ファイルごとに理由を表示し、書けたファイルの印だけを消す。保存の途中(上書き保存・zip の保存とも)に「保存」を押したときは、何もせずに「保存の途中です」の形の理由を表示する。書く前に、ファイルが読み込んだ後にほかで変えられていないかを確かめ、変えられていたら、そのファイルは書かずに、上書きするかやめるかの確認を出す。名前の変更・移動・コピーの後も、この確かめは、そのファイルを読み込んだ(または保存した)ときの中身と比べて行う(移したときの時刻で置き換えない)。ほかで消えていて作り直すファイルは、書く前に同じ相対パスにファイルがないことを確かめ、あれば同じ確認を出す。
- zip の保存(フォルダのハンドルがないとき。ほかのブラウザや、フォルダを選ぶ欄で読み込んだとき): 「保存」で、フォルダの木のすべてのファイル(`.sysml` でないものは中身をそのまま)と、空のフォルダを、相対パスのまま入れた zip を保存する(外部のパッケージを使わず、圧縮しない形式で作ってよい。ファイル名は UTF-8 で書き、その印を付ける)。zip の名前はフォルダの名前とする。保存したら、すべての印を消す。
- 複数のファイルにまたがる図からの編集: 8 章の規則を、書き換えるすべてのファイルに当てる。確かめ(解析し直してモデルの差分を見る)は全ファイルで行い、満たさなければすべてのファイルを書き換え前に戻す。1 回の操作を 1 回の取り消しで、すべてのファイルについて戻す。

段階 C の規則(フォルダの木とファイルの操作。VS Code のエクスプローラーに合わせる):

- 木の欄: テキスト欄の左に、木の欄をいつも置く(フォルダを開いていないときも。幅は分割バーで変えられ、畳める)。畳んだかどうかはブラウザの中(`localStorage` の鍵 `sysmlv2.treeFolded`。値は `1` か `0`)に覚え、次に開いたときも同じにする(フォルダごとでなく、ページで 1 つ。読み書きできないときは、開いた状態で始める)。畳んだときは、開くためのボタンを細い帯に残す。
- フォルダを開いていないとき(1 ファイルのときを含む)の木の欄: 「フォルダを開いていません」、「フォルダを開く」のボタン、「フォルダを開くと、ファイルを分けて書けます。ファイルやフォルダを足す・名前を変える・消すこともできます」の形の短い説明、フォルダをここに置いても開けることを出す。上の帯の「フォルダを開く」も残す。
- フォルダの木: フォルダを開いているとき、木の欄の上に、フォルダの名前と、操作のボタン(新しいファイル・新しいフォルダ・再読み込み・すべて折りたたむ・木の欄を畳む)を置く。ボタンは、HTML の中に書いた小さな SVG のアイコン(文字の色で描く。外部のファイルを読まない)とし、VS Code のエクスプローラーに合わせた形(紙に「+」、フォルダに「+」、丸い矢印、重ねた箱に「−」、左の帯を閉じる形)にする。アイコンは 16×16 とし、木の欄を畳むアイコンは、畳んだときに左右を反転する。マウスを載せたときの説明と、読み上げの名前を付ける。上の帯は 2 段とし、1 段目にフォルダの名前(長い名前は省略し、全文はマウスを載せると出す)、2 段目にボタンを右寄せで、折り返さずに並べる。木には、フォルダの中のすべてのファイルとフォルダを出す(名前が `.` で始まるフォルダとその中は出さない)。各階層で、フォルダを先に、次にファイルを、名前の符号位置の順に並べる。フォルダは開閉できる。
- 名前を変えた・移したフォルダの開閉は保つ(VS Code と同じ)。
- 木の欄の知らせ: うまくいった知らせ(作った・名前を変えたなど)は 5 秒ほどで消す。失敗の理由は、「×」を付けて出し、「×」で閉じるか、次の操作(ファイルの操作の始め、名前の入力欄を出す、ドラッグを始める)をするまで残す。失敗の理由を、続くうまくいった知らせで置き換えない。
- 今のファイルを木の中で強調し、テキスト欄の上の相対パスと一致させる。書き換えたまま保存していないファイルには印を付け、その印をフォルダにも伝える(閉じたフォルダの中に書き換えたファイルがあるとわかるようにする)。
- `.sysml` のファイルをクリックすると、テキスト欄に出す。`.sysml` でないファイルは薄く表示し、このアプリでは開かない(クリックしても今のファイルを変えない)。名前の変更・移動・削除などの操作はできる。
- 操作: 木の項目の右クリックで、新しいファイル・新しいフォルダ(フォルダの項目のとき)・切り取り・コピー・貼り付け・名前の変更・削除を出す。キーでは、F2 で名前の変更、Delete で削除、Ctrl+X・Ctrl+C・Ctrl+V で切り取り・コピー・貼り付けとする(「ファイル」の区画(9.5 節)か、木の欄そのものに焦点があるときだけ。木の欄の上の帯のボタンに焦点があるときも処理しない。「モデル」の区画と参照箇所の欄に焦点があるときは、これらのキーでファイルを操作しない。参照箇所の欄で文字を選んで Ctrl+C を押したときは、その文字をコピーする)。ドラッグで、ファイルとフォルダをほかのフォルダに移す(木の項目はドラッグできるようにする)。木の中のドラッグでは、画面全体のファイルのドロップの表示(「ファイルを置くと開きます」)を出さない。この表示は、外からファイル・フォルダを持ち込んだとき(`dataTransfer.types` に `Files` があるとき)だけ出し、落としたときと、ウィンドウの外に出たときに消す。外から木の欄に落としたものは、画面全体のドロップと同じに扱う。
- 新しいファイル・新しいフォルダ・名前の変更では、木の中に名前の入力欄を出し、Enter で決め、Esc でやめる。焦点が外れたときも、入力した名前で決める(VS Code と同じ。名前の規則に反するときは決めずに、理由を出して入力欄に戻す。ただし、名前が空のまま焦点が外れたときは、やめる)。名前の変更の入力欄では、ファイルは拡張子の前まで(最後の `.` の前まで)を選び、フォルダは名前のすべてを選ぶ。入力欄を閉じたら、焦点を木に戻す。右クリックのメニューは、画面の中に収める。新しいファイルの中身は空とし、拡張子は付け足さない(`.sysml` で終わる名前ならモデルに入り、テキスト欄に出す)。
- 名前の規則: 空でないこと、`/`・`\`・`:`・`*`・`?`・`"`・`<`・`>`・`|` と制御文字を含まないこと、`.` で始まらないこと、末尾が `.` か空白でないこと、Windows の予約名(拡張子を除いた部分が `CON`・`PRN`・`AUX`・`NUL`・`COM1`〜`COM9`・`LPT1`〜`LPT9`。大文字・小文字を区別しない)でないこと、同じフォルダに同じ名前(大文字・小文字を区別しない)がないこと。満たさなければ実行せず、理由を表示する。大文字と小文字だけを変える名前の変更は、フォルダの場合と、`move()` がないときのファイルの場合は行わず、理由を表示する(大文字と小文字を区別しないディスクでは、写す先が元と同じになり、元を消すと中身が消えるおそれがあるため。一度別の名前に変えてから目的の名前に変えれば、同じ結果にできる)。貼り付けで同じ名前があるときは、拡張子の前に「 のコピー」(さらに重なれば「 のコピー 2」…)を付ける。
- ディスクへの書き込みが途中で失敗したときは、その操作で作ったファイル・フォルダを消してから理由を出す(消せなければ、残ったものを理由に書く)。
- 反映の時: フォルダのハンドルがあり、書き込みが許可されているとき(Chrome・Edge)は、操作をその場でディスクに入れる(VS Code と同じ)。書き込みの許可は、最初の操作のときに求める(段階 B と同じ)。ハンドルがないとき(ほかのブラウザ、フォルダを選ぶ欄で開いたとき)は、操作をアプリの中だけで行い、「保存」の zip に入れる。
- 削除: 必ず確認を出し、「はい」のときだけ消す。確認の文に、消すもの(フォルダなら中のファイルの数。削除の前にディスクのそのフォルダの中を読み、木にないもの(名前が `.` で始まるフォルダ・ファイル(`.git` など)と、読み込んだ後にほかで足されたもの)も消えるときは、そのことと数。読めなければ、木にないものも消えることがあると書く)と、「ブラウザから消したファイルは、ごみ箱に入らず、元に戻せません」を書く。書き換えたまま保存していないファイルが含まれるときは、そのことも書く。
- ファイルの名前の変更・移動: ブラウザがファイルの移動(`move()`)を持てばそれを使い、持たなければ、新しい場所に写して中身が同じことを確かめてから元を消す。
- フォルダの名前の変更・移動・コピー: ブラウザの API にフォルダの移動がないので、新しい場所にすべてのファイルとフォルダを写し、すべての中身が同じことを確かめてから、元を消す(移動・名前の変更のとき)。途中で失敗したら元は消さずに止め、その操作で写す先に作ったもの(写し終えたファイルとフォルダを含む)をすべて消してから、理由を表示する。消せなかったものがあれば、それを理由に書き、木にも出す。
- 書き換えたまま保存していないファイルを、名前の変更・移動・切り取りと貼り付けで動かしたときは、書き換えと取り消しの履歴を、新しい相対パスのファイルに引き継ぐ(VS Code と同じ)。ディスクには、動かす前の保存した中身を写す。
- ファイルの操作(作る・名前の変更・移動・コピー・削除)は、テキストの取り消しの履歴に入れない。
- 拡張子を `.sysml` に変えた・`.sysml` から変えたファイルは、モデルに入る・モデルから外れる。操作の後は、全ファイルを解析し直す。ファイルの名前と場所は名前解決に関わらない(6.2 節)ので、`.sysml` のまま名前を変えた・移しただけでは、モデルは変わらない(診断の相対パスだけが変わる)。
- 再読み込み: フォルダの木をディスクから読み直す(ハンドルがあるとき)。書き換えていないファイルは中身を読み直し、ほかで消えていたら木から除く。書き換えたまま保存していないファイルは、今のテキストを保ち(ほかで変えられていれば、保存のときに段階 B の確認を出す)、ほかで消えていたら木に残して印を付け、保存で作り直す。

### 9.5 モデルツリーと参照箇所

大きなモデルをファイルに分けて書くとき、定義と使用の所属と参照を見渡し、目的の記述へ移るためのもの。VS Code のエクスプローラーとアウトラインに倣う。

- 置き場所: 木の欄(9.4 節)を上下 2 つの区画に分ける。上は「ファイル」(9.4 節の段階 C のフォルダの木)、下は「モデル」(モデルツリー)。区画はそれぞれ見出しの行で畳め、境目の分割バーで高さを変えられる。「モデル」の区画の下に「参照箇所」の欄を置き、モデルツリーで選んだ要素を参照している箇所を出す。モデルツリーと参照箇所の欄の境目にも分割バーを置く。木の欄そのものを畳むときは、両方の区画をまとめて畳む(9.4 節)。木の欄を畳むボタンの名前は「木の欄を畳む」「木の欄を広げる」とする。畳んだかどうかは、区画ごとに `localStorage`(鍵 `sysmlv2.filesFolded`・`sysmlv2.modelFolded`。値は `1` か `0`)に覚える(9.4 節と同じ扱い)。
- 区画の高さ: 初めは、フォルダを開いていないときの「ファイル」の区画を中身(「フォルダを開いていません」の形)の高さだけとし、残りを「モデル」の区画に使う。フォルダを開いているときは、「ファイル」の区画を木の欄の高さの 40%、「モデル」の区画を 60% とする。参照箇所の欄は、初めは「モデル」の区画の高さの 40% とする。分割バーで変えた高さは、木の欄の高さに対する割合で持ち、窓の大きさが変わったときは割合から付け直す。フォルダを開いた・閉じたときと、木の欄の上の帯の高さが変わったときも、割合から付け直す。どの区画と欄にも最小の高さ(区画 60px、モデルツリー 40px、参照箇所の欄 56px)を残し、窓を縮めても、区画・欄・分割バーが木の欄の外に出ないようにする(足りない分は、区画の中のスクロールで見せる)。分割バーで変えた高さは `localStorage` に覚えない。
- 1 つのファイルのときも、フォルダのときも出す。1 つのファイルのときの「ファイル」の区画は、9.4 節の「フォルダを開いていません」の形とする。
- 対象: 利用者が読み込んだファイルの要素だけを並べる。標準ライブラリと内蔵する表の要素は並べない(参照先・型として名前だけを出す)。
- モデルツリーの形: 根は大域の名前空間(6.2 節)とし、各ファイルの根の要素(パッケージなど)を、ファイルの並びの順、ファイルの中は記述の順に並べる。子は、持ち主の所有するメンバーを記述の順に並べる。ファイルの木(フォルダとファイル)とは別のもので、ファイルの境目は木の形に出さない(各項目にファイルの相対パスを持たせる)。
- 並べる要素: パッケージ、すべての種類の定義と使用(部品・項目・属性・ポート・接続・インターフェース・状態・行動・計算・制約・要求・ケース・ビュー・列挙など、アプリが解析している種類)、名前がなくても構成をたどるのに要る要素(遷移・継承・接続・結合・流れ・`perform`・`exhibit`・`satisfy`・`send`・`accept`・`assign` など)。`import`・注釈・`doc`・式・値の中身は並べない。`send`・`accept`・`assign` などの行動の引数(送るもの・宛先・経由など、名前を宣言していない引数の特徴)、式を値に持つだけの名前のない特徴(名前のない列挙の値 `enum = 60 [mm];` を含む)、名前のない特徴の連鎖も並べない。
- 項目の表示: 名前(引用符を外す。名前がない要素は、種類と、たどる相手の名前の要約。例: 遷移なら「遷移 A → B」、送信なら「送信 Sig → 宛先」、代入なら「代入 対象」)、種類の日本語名(「書き方」の言葉。9.2 節と同じ)、定義か使用かの印(定義は四角、使用は丸の小さな印。文字の色だけに頼らない)、使用に明示した型と多重度(`: T [1..*]`)。接続・流れ・結合などの要約では、端の名前を、連鎖(`a.b`)を含めて全部出す。並びは、印・名前・型と多重度・種類の順とし、幅が足りないときは、まず種類を、次に型と多重度を、省略の記号を付けて切る(名前はなるべく残す)。ただし、型を出す項目では、型を押せるよう、型に 3em、多重度に 2em の最小の幅を残し、名前が長いときはその分だけ名前を切る(型も多重度もない項目の名前は縮めない)。マウスを載せると、修飾名・種類・型と多重度・ファイルの相対パスと行を出す。名前がない要素の修飾名の区切りは、その要素の要約をかっこで囲んで書き(例: 「(接続 電池.正極 – スイッチ.入口)」)、要約がないときだけ「(名前なし)」と書く(かっこを重ねない)。参照箇所の所属・型の一覧も同じ書き方とする。開閉と選択を保つための同一性の鍵は、この表示の書き方に左右されないよう、表示の修飾名とは別に作る。同じ名前の別の要素は、持ち主の違いと、マウスを載せたときの修飾名・ファイルで見分けられる。
- 型の表示と移動: 使用の型は、解決済みなら押して型の定義へ移れる。型が 2 つ以上なら、押すと型の一覧を出して選ばせる。型の一覧は、解析し直したとき・木を作り直したときに閉じる。型の一覧の項目を押したときは、そのときの解析の結果から移動先を引き直し、古い解析の間なら移らない。型が標準ライブラリ・内蔵する表の要素なら「(標準ライブラリ)」を添え、移らない。未検査・曖昧の型は、その状態の印を付けて出し、押しても移らない(推測した移動先へ飛ばさない)。
- 参照箇所: モデルツリーで選んだ要素(定義・使用・パッケージ)に解決している参照を、すべてのファイルから集めて出す。対象は、名前解決で解決先が決まった参照すべて(型付け・特殊化・再定義・部分集合・参照・接続や結合や流れの端・遷移の元と先・継承の元と先・`perform`・`exhibit`・`include`・`satisfy`・`send`・`accept`・`import` など)。各行に、参照の役割(日本語)、参照している要素の所属(持ち主の修飾名)、ファイルの相対パスと行を出す。行は 2 段とし、上の段に役割の印と所属、下の段にファイルの相対パスと行を出す(所属が長いときは、先頭を省略の記号にして末尾を残す。マウスを載せると全部を出す)。役割ごとにまとめ、件数を見出しに出す。役割は、参照を持つ要素の種類から決め、特殊化の関係にある種類(`exhibit` の状態の使用と `include` のユースケースの使用は、`perform` の行動の使用の特殊化)は、より特殊な種類を先に調べる。`send` の参照は、送るもの・宛先・経由を別の役割とし、`accept` の参照は、受け取る型・経由を別の役割とする。連鎖(`a.b`)の名前は、どの区切りも同じ役割とする。修飾名の途中の区切り(`P::X` の `P`)は、型付けなどの役割でなく「修飾名の区切り」の役割とする。役割の日本語名は、型付け・特殊化・部分集合・再定義・参照(::>)・共役・接続の端・結合の端・割り当ての端・流れの元・流れの先・メッセージの送り手・メッセージの受け手・継承の元・継承の先・遷移の元・遷移の先・perform・exhibit・include・satisfy・satisfy の by・assert・verify・事象(event)・開始(first)・流れの運ぶもの(of)・受け取りの型・受け取りの経由(via)・送信の送るもの・送信の経由(via)・送信の宛先(to)・assign の対象・式の中の参照・import・expose・別名(alias)・依存の元・依存の先・注釈の対象(about)・修飾名の区切り・その他の参照とする。参照箇所は、モデルツリーの子要素とは別の欄に、別の見た目で出し、所有する子要素と取り違えないようにする。未検査・曖昧の参照は、どの要素の参照箇所にも入れない(解決先が決まっていないため)。
- 移動: モデルツリーの項目と参照箇所の行を押すと、その要素(参照箇所の行では、その参照の名前)が書かれているファイルを表示し、その箇所までテキスト欄を送り、字句を選んで強調する。送るときは、選んだ字句がテキスト欄の見える範囲に入るよう、縦と横に送る(9.2 節・9.4 節の診断のクリックも同じ)。字句がすでに見えていれば横の送りは変えず、見えていなければ、字句の始まりを見える幅の左から 4 分の 1 に置く。選ぶ字句は、名前を宣言した要素ではその名前の字句、名前を宣言せずに参照する名前を項目の名前として出す要素(`perform drive;`・`exhibit st;`・`include uc;`・`attribute :>> '光量';` など)ではその参照の名前の字句、それ以外の名前がない要素では宣言の始まりの字句(`entry;` では `entry`、`then s1;` では `then`、遷移では `transition`、状態の後ろの `accept … then …;` では `accept`、接続・結合・割り当て・インターフェース・流れ・メッセージ・送信・受信・代入・`satisfy`・`assert`・制御の節・`if`・ループ・`terminate`・`objective` などではそのキーワード)とする。宣言の始まりは、要素を持つ関係の範囲の始まりから探し、可視性と注の字句は飛ばす。参照する名前が求まらない `perform p.drive2;`・`attribute :>> nope;` などは、参照の最後の区切りの字句を選ぶ。別のファイルへ移るときは、9.4 節のファイルの切り替えと同じく、保存していない書き換えと取り消しの履歴を保つ。テキスト欄で選んだ箇所に合わせて、モデルツリーの項目を選ぶことはしない(後で考える)。
- 開閉と選択: 根の要素は開き、それより下は閉じた状態で始める。解析し直した後も、同じ要素(ファイルの相対パスと修飾名と、同じ修飾名の中の記述の順で同じとみなす)の開閉と選択を保つ。名前を変えた要素は別の要素として扱う(選択が外れ、参照箇所の欄は空になる)。参照箇所の欄で選んだ要素がなくなったときは、欄を空にする。
- 古い解析: テキストを書き換えてから解析が終わるまでの間は、モデルツリーと参照箇所を「解析し直しています」の印を付けて薄く出し、押しても移らない(古い位置へ移らないようにする)。印は、今のテキストの解析の結果が届いたときだけ外す(それより前のテキストの解析の結果が届いても外さない)。押したときに出す知らせ(「解析し直しています。…」)は、今のテキストの解析の結果が届いたら消す。解析が終わったら作り直す。構文エラーのあるファイルの要素は、そのファイルの解析できた範囲だけを出し、ファイルに構文エラーがあることを区画の上に出す。
- 作り直し: 名前の変更・追加・削除・ファイルの操作・再読み込みの後も、解析し直した結果で作り直す。テキストが変わらない解析(ビュー・範囲の切り替えなど)では、モデルツリーと参照箇所を作り直さない(要素の数千の大きなモデルで、ビュー・範囲の切り替えを遅くしないため)。

- **安全性:** 入力の文字列を HTML として実行しないこと。SVG に入る文字列をエスケープすること。XML 1.0 で使えない文字(U+0000〜U+0008、U+000B、U+000C、U+000E〜U+001F、U+FFFE、U+FFFF、対になっていないサロゲート)は U+FFFD に置き換え、保存する SVG がいつも XML として読めるようにすること。ページに Content-Security-Policy を置き、外部への送信と外部からの読み込みを止めること(アプリの動作に要る `blob:`・`data:` とインラインのスクリプト・スタイルだけを許す)。`<script>` などを含む引用符付きの名前などの検査用の入力一覧を作り、図・表の表示と、保存する SVG のすべてで実行が起きないことを確かめる。

5. モデルツリーをキーで操作すること(矢印で項目を選ぶ、Enter で移るなど。9.5 節は求めていない)を、後で考える。
6. 名前解決の既存の不具合: 引用符付きの名前の別名(`package P { part def X; alias 'A' for X; part w : A; }`)を参照すると、`A` が未検査になる(別名の名前の引用符を外さずに持つため)。名前解決の規則と結果を変えるので、後のトラックで直す。
